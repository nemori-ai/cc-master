## 硬闸：动手写第一行实现前

```
命中「值得引入 SDD」的场景 且 此刻无已认可 spec → 停下，先产出/先要 spec，不写产码。
```

这不是建议，是前置条件——与 TDD 的铁律「没有失败的测试，不写产码」同构：这里是「没有已认可的 spec，不写产码」。

判定两步，动手前都要过一遍：

1. **这个改动命中上表哪一行？** 跨边界合约 / 多方消费者 / 接口稳定性要求高 / 并行开发 / 领域复杂不变式密集——命中任一即"值得"，进第 2 步；一条都不占，直接实现，不必等 spec。
2. **若值得，此刻是否已有一份先于实现、被消费方认可的 spec？** 哪怕只是几行接口签名 + 错误契约 + 关键不变式列表也算数。没有 → 先写出它（或先请求一轮 scoping / 向消费方确认关键决策点），再动手写实现代码。

**"acceptance 已经写得很清楚了"不能替代这一步。** acceptance 锁的是外部可观察行为，锁不住内部决策——存储选型、并发/一致性语义、失败模式（fail-open 还是 fail-closed）、状态在重启和多副本之间怎么处置、错误响应的 schema。这些决策若不显式写下来，就会在压力下被默认、被遗忘，又被下一个读者当成"已经想清楚的设计"照单全收。

**时间紧、无人可评审，都不构成跳过的理由——那正是最需要显式化的时刻。** 没有评审者时，spec 就是你唯一能拿来对照检查自己决策的外部标准；跳过它不是省了一步文档，是把一堆本该显式的决定悄悄留给了自己的默认值。
