# 文档对齐：先读齐，改完回写

<!-- ccm:k:start point:preference.doc-alignment -->

合约层面的对齐（规范 → 实现 → 测试）多半已经在你的流程里。这条管的是它旁边那一圈——**README、设计文档、变更记录**——以及一个更早的动作：**动手之前把相关文档读齐**。

**缺省有两条：**

1. **实施前先读齐。** 改一个模块之前，把它的设计文档、相关 ADR、README 里对应的段落读掉。不读就改，你的改动会与一段仍然生效的书面约定悄悄冲突——而那段约定别人还在照着用。
2. **改完回写。** 改动让某段文档变得不再成立，就在同一次改动里把它改过来。**不成立的文档比没有文档有害**：没有文档的人会去读代码，读到过时文档的人不会。

两侧的偏移：

- **偷懒侧** —— 改完不回写。理由通常是「等这块稳定了一起更新」，而「一起更新」的那一天不会到来。
- **过度侧** —— 三行改动配一篇设计文档。文档的成本不在写，在**后来每一次改动都要维护它**；为一个小改动立一份长期负债，是把认真用错了地方。

**判据是这次改动让哪些文字不再成立**，不是改动大不大。改一行配置可能推翻 README 上的一整段安装说明，重构五百行可能一个字都不用改。

**整体是缺省，项目另有约定时让位**，说「另有约定」要拿出证据。

## 失效类型

`motivation_conflict` —— 不是不知道该回写。回写发生在一件事**已经完成**之后，那一刻所有动力都指向收工；而漏掉它当场没有任何代价，代价由几周后读到过时文档的人付。

「先读齐」这一半同理：它发生在开工之前，那一刻所有动力都指向开始动手。**两个动作都落在动力最低的时点上**，这正是它需要成为明文缺省的原因。

## 边界

不管**合约层面**的规范到实现到测试对齐，那已有覆盖；这条只管它周边的叙述性文档，以及实施前的读齐动作。

也不管**该不该写一份新文档**——那是另一个判断。这条只管既有文档与改动之间的一致性。

## 失败形态

漏回写的失败不在当下，在于它**不产生任何即时信号**：测试照绿、评审照过、功能照跑。文档腐坏是唯一一类完全没有反馈回路的债，所以它只能靠明文缺省来防，靠不了自然反馈。
