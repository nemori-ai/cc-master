## 变更纪律：先改 spec

**顺序：spec → impl → test。顺序反了就是让实现偷偷定义真相。**

| 变更类型 | 正确顺序 | 症状（反序） |
|---|---|---|
| 新增行为 | 1. 扩展 spec（新接口 / 新字段 / 新行为示例）2. 写对应测试（先红）3. 实现 | 先写实现，再补 spec，测试验的是实现 |
| 修改行为 | 1. 修改 spec，明确标注 breaking change 2. 更新测试 3. 更新实现 | 实现悄悄偷偷变了，spec 没动，消费者靠 spec 推断的行为不再成立 |
| 删除行为 | 1. 标记 spec 中该条目为 deprecated 或删除 2. 同步通知消费者 3. 删除实现 | 直接删实现，消费者不知道合约变了 |

**breaking change 红线**：如果 spec 的修改使现有消费者的合法调用不再成立，这是一个 **breaking change**，必须显式标注、走版本协商——不能静默发生。静默的 breaking change 是 spec 漂移的一种。

## 失效类型

`motivation_conflict`（主体：行为约束） —— 删掉后，agent 改动行为时容易先动手改实现、事后再补 spec/测试，把'代码即真相'的便宜做法合理化成'反正逻辑是对的'，spec 悄悄漂移却没人被告知。

主体是「先改 spec 再改实现」的顺序纪律，直接动实现是明显更快的近路，动机完美的执行者知道就会遵守。

## 边界

纯探索性 spike——目的就是弄清楚该长什么样而非交付——本身不构成'变更'，可以不先写 spec；但要正式落地时仍必须回到 spec→impl→test 顺序，探索产物不能直接绕过它转正。

## 为什么它随模型变强而更重要

模型越强，对'我已经想清楚该怎么实现'越有把握，也就越容易把先写 spec 当成给自己设的形式主义关卡跳过——它构造的理由通常是'我心里清楚，不用先写下来'，而这恰是最该被写下来的时刻。

## 失败形态

隐蔽违反：确实先提交了 spec 改动、顺序看着合规，但写着写着实现改用了另一个方案，却没回头同步 spec——commit 顺序检查会通过，但两者内容对不上，比根本不写 spec 更难被发现。
