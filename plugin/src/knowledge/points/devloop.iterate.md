## 心智锚 2:dev loop = 迭代优化,不是一次成型

**propose 改动 → 测量 → 读梯度 → 调整 → 重复。** 小步、每步测量,优于"写一大坨再跑"——后者等于一步迈到谷底、放弃了沿途所有方向信息。每一轮的产出不是"更多代码",是"更小的 loss + 一点关于下一步往哪走的信息"。

把每一轮当成一个可证伪 hypothesis:"我相信改 X 会因为 Y 降低 loss。"然后做最小有用干预并测量。说不出 hypothesis 却继续写代码,通常是在用 churn 假装优化。

## 失效类型

`motivation_conflict`（双重性质·方法部分更强的模型能自己补回来，留下的是约束） —— 删掉后,执行 agent 仍然知道小步测量比一把梭好,但在'我很确信这次是对的'的自信或赶进度的压力下,会选择跳过中间测量、一次性写一大坨改动再统一验证。

小步改动+每步测量+可证伪假设是公共的迭代优化常识，模型能自己补出，缺的是不图快写一大坨。

## 边界

例外仅限于中间状态本身不可被有意义地测量的原子变换(例如一次跨多文件的重命名,改到一半时代码根本无法编译/运行);这类变换客观上没有可测量的中间态,不是因为分步更慢而跳过分步。

## 为什么它随模型变强而更重要

模型越强,一次性写出的大批改动'恰好整体正确'的命中率越高,这种更高命中率反而更容易让人倾向于跳过分轮测量——但一旦命中率之外的那次出错,大改动纠缠在一起,定位问题的成本并不会因模型变强而降低,反而因为改动更大而更难拆解。

## 失败形态

agent 在大改动前先写下一句'我相信改 X 会因为 Y 降低 loss'的假设做出仪式感,随后一次性完成大改动并直接宣称验证通过,却从未真正跑过测量;或者把好几轮改动打包成一次性的'大改动+一次测试',测试过了就回填出一份看似分轮迭代的叙事。
