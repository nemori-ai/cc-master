## 何时值得 SDD，何时过重

SDD 不是对一切代码适用的万能方法——spec-first 带来的收益在某些场景巨大，在另一些场景是额外摩擦。

### 值得引入 SDD 的场景

| 场景 | 原因 |
|---|---|
| **跨边界合约**（服务间 API、库的公共接口、事件总线消息格式）| spec 是两侧唯一的对齐点，没有 spec 任何一方都可以单方面破坏合约 |
| **多方消费者**（一个接口有多个独立调用方）| 没有 spec 则"哪些行为被依赖"只存在于各消费者的脑子里，一旦实现变化影响范围无法推断 |
| **接口稳定性要求高**（向后兼容窗口长）| spec 是 breaking change 的精确标尺 |
| **并行开发**（前后端 / 服务 A 与服务 B 同时开发）| 先冻结 spec，两侧可以同时用 mock 开发，不用等对方实现上线 |
| **领域复杂、不变式密集**（金融、医疗、权限）| spec 显式记录不变式，否则只存在于实现者的隐性假设里 |

### 过重的场景

| 场景 | 原因 |
|---|---|
| **探索性 spike / PoC**（目标是发现问题，而非交付合约）| spec 预设你已经知道要做什么；spike 的目的是发现你不知道的 |
| **单消费者的内部小函数**（实现与消费在同一文件、同一作者）| 合约成本 > 收益；直接改实现 + 改测试的成本远低于维护独立 spec |
| **快速实验，预期会大幅重写**（想法尚未收敛）| 早期冻结 spec 会锁死设计空间；等想法稳定再写 spec |

这与「正则化=简单性」这一认识论立场呼应：不是所有代码都需要同等重量的工程手艺，选对场景才有收益。
