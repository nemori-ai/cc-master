# 评审评哪些维度

<!-- ccm:k:start point:preference.review-scoping -->

谁来评审已有讲法（评审者要与实施者异质）。这条管另一件事：**这次评审要看哪几个维度，以及维度数量该随什么伸缩。**

**缺省的伸缩依据是「错了的代价」，不是改动大小。**

- 一处**难以回滚**的改动（数据迁移、对外接口、发布物），维度要铺开：正确性、兼容性、失败模式、回滚路径。
- 一处**当场可撤**的改动（内部实现、测试、文档），一个维度就够：它做到它说的了吗。

三行的数据迁移比三百行的内部重构更该被多角度看，**行数在这里几乎不携带信息。**

两侧的偏移：

- **偷懒侧** —— 不评审，或者只扫一眼「看起来对」。
- **过度侧** —— 每次改动都跑一遍全维度清单。多余的维度不是免费的：它们稀释注意力，让真正该被盯住的那一维得不到应有的重量，**评审因此变得更弱而不是更强。**

同样地，**每个维度都要落到一个具体的判据**——「安全性」不是维度，「这个输入路径上有没有未校验的外部数据」才是。说不出判据的维度，不会真的被评，只会被写在清单上。

**整体是缺省，项目另有约定时让位**，说「另有约定」要拿出证据。

## 失效类型

`motivation_conflict` —— 按代价选维度这个道理不难。走偏来自两个方向的省力：省事就不评，或者反过来，把全维度清单跑一遍——后者看上去更负责，实际上是**用穷举替代判断**，因为穷举不需要想。

过度侧在这里尤其隐蔽，它伪装成认真。

## 边界

不管**谁来评**（已有覆盖），只管**评什么**。

也不管评审发现之后怎么处置——那属于收敛与打回的判断。

## 失败形态

最常见的形态是清单化：一份固定的评审维度表被无差别地套在每次改动上。它形式上覆盖率 100%，实质上每一维都只得到 1/N 的注意力，**而那次改动真正的风险点恰好只需要其中一维得到全部注意力。**
