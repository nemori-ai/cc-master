## 设计 → 开发 → 测试：何时取哪把刀

| 阶段 | 主用理论 | 这一刀回答什么 |
|---|---|---|
| **动手前（硬闸）** | SDD | 命中值得 SDD 的场景、且无已认可 spec → 停下先产出 / 先要 spec，再动手写产码 |
| **设计** | DDD + SDD | 领域怎么划 / 建模？合约先长什么形？ |
| **开发** | OOP + SDD | 类 / 对象怎么写到品味线？实现怎么对齐 spec？ |
| **测试** | TDD | test-first 这条纪律具体怎么执行？ |
| **横跨三阶段** | 五条根 + 红线 | 始终成立的脊椎 |

**四理论是接力，不是并列**：SDD 冻结合约形状 → DDD 在其上划 bounded context 与不变式所有权 → OOP 实现到合约 → TDD 对着合约红绿。这条接力顺序管的是「哪种手艺在哪阶段**领跑** + 合约先行」，**不是**「相位闸、不许回头」——它是**典型领棒次序**，**不是瀑布**。

它跑在三个尺度上：①**顶层敏捷**（目标纵切薄增量 / walking skeleton / 按 cadence 交付）；②**片内有序**（每薄片端到端走 SDD→DDD→OOP→TDD 四棒）；③**任务内迭代**（片里每个 dev 任务按 propose→measure→adjust 逼近验收）。迭代循环在每一棒**内部**跑，与接力次序不同尺度、不打架。

②与重型瀑布差在三轴，别混：**范围**=一薄片非整个项目 / **反馈**在每片边界就回来非攒到最末 / 与③**共存**。

## 失效类型

`capability_gap`（主体：事实方法） —— 模型通常不知道SDD/DDD/OOP/TDD这四种理论该怎么在同一个开发流程里配合,默认要么只用其中一种、要么把它们当严格瀑布顺序执行;这套三尺度接力关系是本项目发明的综合框架,不教就不会用。

主体是阶段选刀方法：SDD→DDD→OOP→TDD 的领棒次序、它为何不是瀑布、以及顶层/片内/任务内三尺度的对应关系。

## 边界

只适用于足够复杂、值得走完设计-开发-测试链路的变更;单纯改错别字或调一个配置值这类不含设计决策的改动,不落在这套接力关系管辖的范围内。

## 失败形态

表面上遵循了"先设计再开发"的顺序,但把典型领棒次序读成了不可逆相位闸——开发时发现设计有问题也不敢回头改设计文档,理由是"已经进入开发阶段了";这种把接力误读成瀑布的形态,恰恰违背了这条知识要澄清的核心。
