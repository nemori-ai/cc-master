## 心智锚 3:测试 / 检查 = 你的测量仪器(梯度的来源)

没有测量,优化就是闭眼下山。**先架好仪器,再下降**——这正是 TDD 的优化学解读:先写验收 / 测试 = 先把目标函数和测量装置摆好,之后每一步都有读数。

- 一次**失败不是噪声,是梯度**:它精确告诉你"哪里、往哪个方向调"。**读懂这次失败** > 盲目再改一版。
- 测不了的东西优化不了。任务里若有"说不清怎么测"的验收维度,那一维你是闭眼的——把它变可测,或显式标注它没法机械验收(留给人验)。
- 先校准仪器,再相信梯度:flaky test、错 endpoint、mock-only 检查、过期 fixture、不可复现失败,都会给你假梯度。本 skill 只讲 TDD 的红绿铁律和 constraint parity 在优化 loop 里的位置。

## 失效类型

`capability_gap`（主体：事实方法） —— 知道要先读懂失败信号再改下一版、要先确认仪器本身可信，但在想尽快看到绿灯的心态下，会倾向于跳过诊断直接换个方向再试，或不假思索地相信一次凑巧变绿的结果。

主体是「先架仪器再下降、失败即梯度、先校准再信读数」的测量方法论。

## 边界

只对存在反复迭代、可以积累读数的收敛过程有意义；一次性、没有第二轮机会的纯创造性交付本身没有“梯度”这个对象可用，不是可以省略的情形，是压根不适用。

## 失败形态

失败出现后没有去改被测的实现，而是直接改测试断言让它变绿——形式上红绿灯还在跑、还是绿的，仪器看起来仍然有效，实质是把测量装置改成了配合既有（可能有问题的）实现说谎的仪表盘。
