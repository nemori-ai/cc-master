# 什么时候看花名册、什么时候读收件箱

<!-- ccm:k:start point:coordination.consumption-triggers -->

两条命令：

```
ccm peers list --json                        跨板花名册：谁在跑、目标是什么、负载与优先级、心跳是否新鲜
ccm coordination inbox list --unconsumed --json   收件箱里还没处理的通知
```

**触发点固定挂在每回合的侦察步上**，和你读板、读配额是同一个动作里的事。理由是这两样都属"外部世界这一刻的状态"，而不是"有需要时再去查的资料"——**有需要时你才想起去查，说明你已经错过了它该起作用的那一刻。**

除了每回合侦察，三个额外时机值得单独跑一次：

- **准备派发一批并行任务之前** —— 这时候撞车成本最高，事后才发现要重解冲突。
- **准备把一个节点推向合并 / 发布之前** —— 顺序在这里直接变成代价。
- **配额吃紧、正要决定降档或停下时** —— 中介的配速建议正是按同一批共享资源算的。

**读完就 ack**（`ccm coordination inbox ack <id> --note "…"`）。不 ack 的后果不是通知丢失，是你下次分不清哪些看过哪些没看过，于是每次都要重读全部，于是很快就不读了。

**通知会腐。** 它们带过期时间，但过期只保证消息还躺在那儿，不保证有人及时看。上面那次积压里的配额警告，写的时候是 95%，读到时实际是 56%——**照着一条过期的配额警告去决策，比不读更糟。** 读到的每一条先看它是什么时候写的。

## 失效类型

`environment_fact` —— 主体是本工具的两条命令、它们各自答什么，以及在这套编排节奏里该挂在哪几个点上。

「协调要知道别人在干什么」这个道理不用教。**命令叫什么、收件箱这个概念存在、触发点挂在侦察步上——这些是本产品的具体事实，更强的模型一样推不出来。**

按顺序过滤器：主体是事实与方法，不是行为约束；把方法交给更强的模型，它补不回命令名与时机锚。故归这一档，且这一档随接口自我说明能力提升而贬值——哪天这些信号自动进上下文，这条就该退役。

## 边界

不管**读到之后怎么判**（那是消费原则那一条），只管什么时候去读。

也不管订阅注册这类会话绑定的机制细节。

## 失败形态

真实记录里，那次跨板盲区是被一句**与协调毫无关系**的通用完整性自检偶然撞上的——「每一件该做的事都真的做了吗，包括还没登记在板上的」。全仓能撞上跨板盲区的只有这一句，而它撞上纯属偶然。**没有触发点的能力，等于没有这个能力。**
