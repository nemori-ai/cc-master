## 权威陈述

<!-- ccm:k:start point:multilayer.maintenance -->
执行者产出并维护的计划文档，落在**被编排项目约定的位置**——那个项目的 `PLAN.md` / design doc 目录 / 它自己的 planning skill 产物等，**按该项目的约定走**，不是 cc-master 指定一个固定文件名。它一物两用：① 单任务*内部*分步的可追溯记录（决策 / 取舍 / 已完成 / 待办）；② 续跑 / 换 session 接手的锚点（下一个执行者从它接上手）。

与 board 的分工要钉清楚：

| | cc-master board | 被编排项目的计划文档 |
|---|---|---|
| 管什么 | 跨任务：依赖 / 并行 / 派发 / 验收 | 任务内：一个大节点内部怎么分步走 |
| 视角 | 横向（任务之间） | 纵向（一个任务之内） |
| 落点 | gitignored home，**不入被编排项目版本控制** | 被编排项目约定的位置（多半入它的版本控制） |
| 续跑用途 | 你跨 compaction / session 的记忆 | 执行者在单节点内续跑 / 换手的锚点 |

两者都服务「可续跑」，但尺度不同：board 让**你**记得整张图，项目计划文档让**执行者**记得这一个节点内部走到哪了。端点验收时，board 节点的 done 仍以**你自己端点的独立验收**为准（见 `resume-verify.md`），项目计划文档是执行者的工作记录、不替代你的验收。
<!-- ccm:k:end point:multilayer.maintenance -->

## 失效类型

`environment_fact`（主体：事实方法） —— 删掉后执行者不知道内部分步记录该落在哪、该怎么落——可能干脆不维护，也可能塞进不该塞的地方，跨 session 接手时找不到锚点，只能从头摸索这个节点内部走到哪了。

主体是计划文档落点与 board 的分工事实（board 在 gitignored home、不入被编排项目版本控制），是本项目约定。

## 边界

一个任务如果内部本身就是单步、不可再分（没有中间决策 / 取舍 / 阶段性产物需要追溯），就没有维护对象——这类节点不需要专门的计划文档，不是「偷懒可以不写」，而是没有值得记录的内部分步过程。

## 失败形态

执行者确实写了一份文档、放在看似合理的位置，但内容只是任务描述的复述或结果摘要，没有记录中途的决策与取舍——换手的下一个执行者打开文档看不出「为什么走了这条路、放弃了哪条路」，形式上有文档，实质上没有可续跑的锚点。
