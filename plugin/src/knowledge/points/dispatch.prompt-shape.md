# 派发 prompt 该长什么形状

<!-- ccm:k:start point:dispatch.prompt-shape -->

契约必须含哪些字段是另一回事（输入依赖、输出形状、成功判据、时限与预算、升级条件），那是骨架。这条讲骨架撑起来之后，**正文该写什么**。

**形状是：给目标和判据，不给步骤和方案。**

一份够用的派发 prompt 有五块：

| 块 | 写什么 | 为什么它非有不可 |
|---|---|---|
| **背景** | 这件事为什么存在、上游是什么 | 执行者没有你的上下文。缺了它，它只能猜意图，而猜错的方向往往看起来很合理 |
| **目标** | 做到什么算完 | 不是"做这件事"，是"做完之后世界是什么样" |
| **边界** | 明确不要碰什么 | 它不知道你的全局，最容易越界的恰恰是它觉得顺手的地方 |
| **自证** | 它怎么证明自己做到了 | 没有这个，你收到的是一句"完成了" |
| **求助条件** | 遇到什么就停下来问，而不是自己决定 | 它默认会自己决定 |

**不写**：实现步骤的逐条分解、文件级的改法、函数与变量的命名、你脑子里那个方案的复述。

判据是**它拿不到还是它做不到**：

- 它**拿不到**的（项目背景、上游意图、你知道而它不知道的约束）→ 必须给。
- 它**做得到**的（怎么实现、怎么组织代码、用哪个库）→ 不要给。给了不是帮忙，是把一个有判断力的执行者降格成打字机。

这两类经常长得很像，因为写下来都是"多说一句"。区别在于删掉之后它会不会做错：**删了会做错的是信息，删了只是做法不同的是你的偏好。**

## 失效类型

`motivation_conflict` —— 不是不知道派发 prompt 该怎么写。是压力下两侧各有一个省力出口：赶时间就把方案钉死（省得来回），图省事就丢一句"把这个做了"（省得组织）。

两个出口都不需要任何能力缺陷就能走进去，且都在当下显得合理——前者叫"说清楚点免得返工"，后者叫"信任执行者"。

## 边界

不管**契约字段清单**（那已有覆盖），只管字段之外的正文。

也不管**针对特定模型的写法偏好**——那一层与目标模型有关，会随模型换代变化；这一层与目标模型无关，是编排者自身的纪律。

## 失败形态

欠指定那一侧的失败很响：执行者做错方向、交回来的东西对不上、返工一轮。**它会被立刻发现，所以它会被修。**

过度指定那一侧完全无声：执行者照你说的做了，做出来的正是你想的东西，测试也绿。你会觉得这次派发很成功。**没有任何信号告诉你，你刚才花了一次派发的成本，买回了自己已经知道的答案。**
