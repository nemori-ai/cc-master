# 派发 prompt 的最小约束红线

<!-- ccm:k:start point:dispatch.prompt-red-lines -->

品味有伸缩空间，这几条没有。

**绝不能写进去：**

- **你已经想好的实现方案的逐步分解。** 见下，这是本条最要紧的一句。
- **凭据、密钥、原始输入数据。** 派发 prompt 会被记录、会被传递、会进日志。
- **你没有亲自验证过的"事实"。** 记忆里的接口签名、猜的文件路径、觉得应该存在的命令。**执行者会当真，并在错误的前提上把整件事做完。** 不确定就让它自己去查，那比给一个错的起点强得多。

**绝不能省：**

- **怎么算做完。** 一个它能自己跑、能给出是或否的判据。没有它，你收到的必然是自我评估，而自我评估的乐观是系统性的。
- **什么时候停下来问。** 不写，它就会自己决定；而它不知道哪些决定超出了它的授权。
- **并行时的隔离位置。** 工作树的绝对路径，写死在 prompt 里。
- **它拿不到的最小背景。** 少给会让它猜，而猜错的方向通常看起来很合理。

---

**关于第一条：把方案钉死到执行者只剩打字，是「指挥不演奏」的一次隐蔽违反。**

现有的红线抓的是"你自己动手写代码"。它抓不到这个形态——**你确实派发了，确实没有自己写。** 形式上每一步都合规。

但实质上：方案是你想的，判断是你做的，取舍是你定的，执行者只是把你脑子里已经成型的东西逐字打出来。**这和亲手做的唯一区别，是多了一个执行者。**

判它有个干脆的问法：

> **如果这个执行者比你更懂这一块，你这份 prompt 里有哪一句会挡它的路？**

答案是"没有"时，你给的是目标和判据。答案是"好几句"时，你给的是自己的方案——而那几句正是你该删掉的。

## 失效类型

`motivation_conflict` —— 每一条的反面都不是无知，是压力下的省力或求稳。

尤其是钉死方案那一条：它由**焦虑**驱动而非懒惰——怕执行者做偏、怕返工、怕不可控。而由焦虑驱动的违反最难自我识别，因为它在当下的感受是"负责任"。

## 边界

不管**该不该派发这件事**（那是路由与切分的判断），只管决定要派之后，prompt 里什么不能写、什么不能省。

秘密不进 prompt 这一条与既有的安全边界重合，此处只作为红线清单的完整性收录，不重复它的理由。

## 失败形态

隐蔽违反的要害在于**它通不过任何现有的检查**：派发记录在案、执行者独立跑完、产物有人交、测试是绿的。从外面看，这是一次教科书式的派发。

只有一个东西不对——**这次派发没有产生任何你原本没有的东西。** 而没有一个指标会报告这一点。

> 「钉死方案 = 指挥不演奏的隐蔽违反」这层关系，本该由一条指向那条红线的导航边表达。**这条边现在建不出来**——跨越技能边界的边尚未开放。所以这层关系只能靠上面的正文自己说全，不能指望导航把读者带过去。与「不收敛作诊断信号」缺的那两条边同源，一并等结构放开后补。
