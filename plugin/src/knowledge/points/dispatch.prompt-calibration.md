# 约束到什么程度算刚好

<!-- ccm:k:start point:dispatch.prompt-calibration -->

每写一句进派发 prompt，问一次：

> **这一句是在补它拿不到的信息，还是在替它做它能做的判断？**

前者留，后者删。这一问能处理绝大多数具体情形，因为它对准的是唯一真正相关的差异——**你和执行者之间的信息差**，而不是"说清楚点总没坏处"这种直觉。

四条常见的落点：

| 情形 | 怎么处理 | 为什么 |
|---|---|---|
| 它已经会的事（怎么写测试、怎么用这门语言、常见模式） | **别教** | 教了不增加正确率，只增加它要读的字数，并暗示你不信任它的判断 |
| 验收判据、停止条件、升级条件 | **绝不能省** | 这些不是它会不会的问题，是它**没有**你才有的那份标准 |
| 项目的具体事实（配置在哪、约定是什么） | **指路径，别抄** | 抄进 prompt 的那一刻它就开始过期，而且它抄错了你不会知道 |
| 实现方案 | **别写死** | 见下 |

**把实现方案写死会让结果变差，不只是浪费。** 一个被钉死到只能照做的执行者，不会告诉你方案里那个你没想到的坑——它没有余地去发现，因为你没给它需要判断的地方。**你换来的确定性，代价是失去了第二双眼睛。**

而且这条有个更麻烦的性质：**方案钉得越死，看起来越专业。** 一份写满具体步骤的派发单读起来比一份只给目标和判据的更像认真准备过。评价信号偏向前者，正确答案通常是后者。

**这整件事是你在写这份指导时做的同一道题的微缩版**：给一个有能力的对象多少指导才合适。答案在两边是一样的——**补它缺的那一半，别替它做它能做的那一半。**

## 失效类型

`motivation_conflict` —— 判据本身不难，难在两侧都有省力出口，而且过度那一侧伪装成认真。

尤其是"多说一句总没坏处"这个直觉：它在单句上永远成立，累加起来就是把执行者写成了打字机。**每一句都无害，总和有害**，这是典型的动机型失败而非能力型。

## 边界

不管**该给哪些骨架字段**，也不管**面向某个具体模型该用什么措辞结构**——后者随模型换代变化，这条不随。

只管"该给多少"。

## 失败形态

真正的代价不在这一次派发，在它训练出的习惯：**每次多写一点、每次都成功、于是每次写得更多。** 因为过度指定从不失败——它只是让每次派发的净收益趋近于零，而这个趋近过程没有任何一处会报警。
