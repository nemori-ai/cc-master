# 等用户，不是各自等，是在排队

<!-- ccm:k:start point:hitl.cross-board-queue -->

把一个节点标成"在等用户"，表达的是单板视角的一件事：我卡住了，等人拍板。

它**表达不了**另一件同时为真的事：另外两块板也在等同一个人，**而这三件事的处理顺序直接决定总代价。**

那个真实的例子里，三个合并请求同时挂着等同一个人，两两重叠十五、三、一个文件。**谁先合，谁就让另外两个去重解冲突。** 顺序的代价差是实打实的，而三块板里没有任何一块能自己决定这个顺序——它们各自只知道"我在等"。

所以当你发现自己在等用户，而花名册显示同侪也卡在用户关口上时，多做一步：**把顺序建议连同代价差一起交上去**，而不是安静地各等各的。

一份够用的形态：

> 三处都在等你。建议顺序 B → A → C。
> 先 B：A 与 C 各需重解 3 个文件。
> 先 A：B 需重解 15 个文件。
> 差额约十二个文件的冲突解决。

**你交的是排序建议加代价，不是催促。** 拍板的仍然是人——他知道你不知道的事（哪件更急、哪件今天不想碰）。你补的是他手上缺的那半份信息：**他能看见三件事都在等他，看不见它们之间的先后会差出多少。**

这件事你不做，就没有人做。中介算的是配速与资源，不算人的注意力顺序；别的板和你一样只看得见自己。

## 失效类型

`prosthetic` —— 与"建议只有被读才产生价值"同源：跨板视野是结构性缺失。

你看不见别的板也在等同一个人，这不是判断失误，是**视野里根本没有那块地方**。更强的模型不会因此看得见——竞争关系不在它的上下文里，推不出来。

不是不愿意排队，是不知道自己在队列里。

## 边界

不管**单板内**的等待处理：怎么组织决策包、怎么给足上下文让人一次拍完，那些已有讲法。这条只管多块板竞争同一个人时多出来的那一层。

也不管重叠面**怎么算**——那是它的前置，算不出重叠就估不出顺序代价。

## 失败形态

三块板各自安静地等，每一块的行为都无可指摘：都标了在等用户、都给了决策包、都没有催促。**代价不落在任何一块板上，落在它们之间**——而它们之间不属于任何一块板的视野，所以没有任何一处会报告它。
