## 根 4：分层思维

把「**算什么**」和「**从哪取 / 往哪写**」分开，依赖**只许从外朝里指**。

- 依赖**单向**：domain 不依赖 persistence / web；外层实现内层定义的接口。
- **编排与规则分离**：应用层纯编排（拉数据、发事件），领域层纯规则（不碰 I/O）。**双因改变的症状是测试要 mock 一堆 I/O**——那是该拆的信号。
- 测试随之分层：domain → unit（无 I/O），边界 → integration（对真实后端）。

## 失效类型

`capability_gap`（主体：事实方法） —— 删掉后,agent 抽象上可能仍认可领域不该依赖基础设施,但没有『测试要 mock 一堆 I/O 就是该拆分的信号』这类具体诊断技巧,遇到规则与 I/O 混写的代码识别不出来,也不知道该往哪条边界拆。

主体是分层与依赖方向的方法框架（算什么 vs 从哪取、编排与规则分离、测试随之分层），并给出「测试要 mock 一堆 I/O」这个诊断信号。

## 边界

只对『规则会变』或『规则需要脱离具体 I/O 实现单独验证』的代码适用;一次性脚本、或 I/O 本身就是全部逻辑(没有可独立验证的规则部分)的场景,不构成需要分层的对象。

## 失败形态

代码表面上有一个 service 层和一个 repository 层,文件结构看起来分层齐全,但 service 层函数里直接拼 SQL、或直接按 HTTP 状态码分支决定业务结果——结构像分层了,规则其实仍耦合在 I/O 细节上;它自己的测试已经证明了这点:domain 测试必须 mock HTTP client 才能跑,却没人对照这个信号回头拆分。
