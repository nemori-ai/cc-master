## spec 是什么 / 不是什么

### spec 是

| 元素 | 说明 |
|---|---|
| **接口签名** | 函数 / 方法 / API 端点的名称、参数类型、返回类型——先于实现冻结 |
| **数据 schema** | 输入 / 输出 / 事件 / 命令的结构定义（字段名、类型、必选 / 可选、枚举值）|
| **错误契约** | 哪些错误路径 / 哪些异常类型 / 哪些状态码是合法输出的一部分 |
| **不变式** | 在所有调用前 / 后 / 过程中必须保持成立的约束（前置条件 / 后置条件 / class invariant）|
| **行为示例** | 给定输入 → 期望输出的具体示例（比类型签名更精确地锁定语义）|
| **ubiquitous language** | spec 里的术语与 DDD 领域语言对齐——同一概念只有一个词 |

### spec 不是

- **事后补的文档**：如果 spec 是从已有实现里逆向生成的，它描述的是"现状"不是"合约"——它不能作为判断另一方行为正确与否的标准。
- **实现细节的记录**：算法选择、数据结构偏好、私有字段命名——这些不在 spec 里，属于实现方自由裁量。
- **不可改变的石板**：spec 可以演化，但**演化必须显式——先改 spec，再改实现**（见「变更纪律」一节）。

## 失效类型

`capability_gap`（主体：事实方法） —— 删除后,agent 分不清 spec 该装什么、不该装什么——容易把实现细节写进 spec 造成不必要的频繁变更,或把逆向生成的现状文档当成权威契约来遵守。

主体是「什么算 spec、什么不算」的判据清单，缺了就分不清合约与事后文档、实现细节的边界。

## 边界

本条只做什么算 spec 内容的静态分类,不覆盖值不值得为这部分单独投入写 spec 的场景取舍——即使理论上够格是 spec 四要素,遇到一次性脚本或纯内部私有函数,仍可判定不必单独出正式 spec,这不算违反本条边界。

## 失败形态

写出来的 spec 表面上列了接口签名和数据结构,像模像样,但混进了具体用哪种排序算法、内部用什么容器存储这类实现细节,让实现者误以为这些细节也被冻结、不敢做等价重构;或把逆向生成的行为文档包装成 spec 发布,读者分不清哪些是承诺、哪些只是现状巧合。
