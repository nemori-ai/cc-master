# 默认隔离实施

<!-- ccm:k:start point:preference.isolated-implementation -->

**缺省：任何会写文件的实施，都在自己的工作树里做，不在主检出上直接动手。** 并行时这是硬要求（两个 writer 共用一棵树必然互相踩），单任务时它仍是默认——因为主检出是你观察全局的地方，它一脏，你就失去了「当前干净状态」这个基准。

**并行的拓扑：一个 hub，每个执行者一棵自己的树。** 不是每个执行者再往下分叉，也不是几个执行者共用一棵。

两侧都会走偏：

- **偷懒侧** —— 直接在主检出上改，理由通常是「就一行」。一行改动的隔离成本确实高于收益，但**判断「就一行」的那一刻你还没开始做**，而估错规模是常态。
- **过度侧** —— 改个错别字也开一棵树。隔离是手段不是仪式，为不产生冲突风险的改动付隔离成本，就是把纪律执行成了负担。

分界线在**这次改动会不会与别处并发**，不在改了几行。会并发就隔离，不会就别为形式付账。

**这条整体是缺省，项目另有约定时让位。** 说「另有约定」要拿出证据。

<!-- ccm:k:end point:preference.isolated-implementation -->

## 失效类型

`motivation_conflict` —— 怎么开工作树不是知识问题。走偏发生在压力下：赶时间就直接改主检出（省一次切换），或者反过来，把隔离当成显得规范的仪式，无差别地开。

两侧都是倾向问题，不是能力问题，所以归这一档。

## 边界

**不含收口约定**——谁能提交、怎么合并、分支怎么命名、什么时候清理，这些每个项目都不一样，必须去项目里发现，不能带着一套预设进去。

尤其不要把某个项目「执行者绝不自己提交」这类收口纪律当成普适倾向带出去：别的项目完全可能让每个执行者自开 PR，那是它们的选择。

**可以带的**：默认隔离、hub 加一执行者一树的拓扑。**必须去发现的**：提交权、收口方式、命名、清理时机。

## 失败形态

它是让位机制的第一个真实样例，也最容易示范错：把一个具体项目的收口纪律**连同**通用的隔离倾向一起带出去，看上去只是"多给了一点指导"，实际上是拿一个项目的内部约定去覆盖别的项目的选择——而那正是让位机制存在的理由。
