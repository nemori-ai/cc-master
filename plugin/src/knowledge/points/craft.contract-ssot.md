## 根 2：契约即 SSOT

每个边界都有一份**先达成、被双方共同遵守**的合约。它在哪定、谁拥有、**改它的顺序**，比任何实现细节都先。

- **SDD**：spec 是**先于实现**的合约单一真相源——**整条 SDD 立在这根上**。改合约先改 spec，再改实现与测试。
- **DDD**：ubiquitous language 锁定术语；事件 / 命令 / 枚举名来自合约源，**临时起名在集成时必死**。
- **OOP**：domain 拥有接口 / Protocol，**不靠 wrapper 翻译**（DIP 的合约就是 spec）。
- **TDD**：test double 必须强制与真实后端**同样的约束**（constraint parity）——否则你测的是 mock 不是世界。

## 失效类型

`motivation_conflict`（双重性质·方法部分更强的模型能自己补回来，留下的是约束） —— 删掉后模型仍清楚"契约应该在前"是好实践，但撞上"先改代码更快、稍后补 spec"或"这个 mock 差不多够用了"这类现场诱惑时，容易先斩后奏，把补合约留到"以后"，而"以后"往往不会发生。

spec 先于实现、统一语言、domain 拥有接口、test double 约束对等都是公共工程共识，模型懂，只是赶工时先改实现后补合约。

## 为什么它随模型变强而更重要

强模型更擅长论证"这次先改实现、稍后补 spec 也不影响正确性"之类站得住脚的理由，把顺序颠倒包装成对结果无影响的等价改动；模型越强，这种事后自圆其说就越有说服力，越难被看出合约其实已经先斩后奏地漂移了。

## 失败形态

最隐蔽的形态是顺序被悄悄倒置却留下一份事后追认的合约——先在实现里改完，再回头把 spec 补齐到看起来像是先写的；或者 test double 的接口签名和真实后端完全一致，但对错误路径的约束被悄悄放宽，测试全绿，测的却是一个比真实世界更宽容的假想世界。
