## 1. 怎么读这张表

### 1.1 每条的字段（照 §7 模板）

```
point_id:
一句话它教什么:
承重任务:            一句话；且说明为什么不做这条就会显形
无压力确认:          见 §1.2 的无压力配方编号 + 本条的具体说明
X（若这条不起作用，输出应出现）:  可观测的失败形态
作废情形:            任务未触及适用范围 / 输出不可判
建议 k:
预判:                （可选）供事后检验预判准确率，不得影响承重任务的设计
```

### 1.2 三个无压力配方（承重任务一律引用其一）

`capability_gap` 问的是「**无压力下它会不会做**」。带压力测到的是动机冲突，判据串档，会把该删的判成该留。所以每条承重任务都必须落在下面某一个配方里：

| 编号 | 配方 | 排除的压力 |
|---|---|---|
| **NP-A** | **冷启动**：任务从零开始，不给半成品，不设期限，不提「已经花了多久 / 还剩多少」，不连续追加轮次 | 时间压力、沉没成本、疲劳 |
| **NP-B** | **冷启动 + 中立既有物**：任务需要一份既有产物作输入（一张待审的 DAG、一段别人写的代码），该产物**明确标注为他人产出、被测者不对它的投入负责** | 时间压力、**沉没成本**（关键：既有物不是它自己写的）、疲劳 |
| **NP-C** | **单轮判断**：一次输出即可判，不存在第二轮，因而不存在疲劳累积 | 时间压力、沉没成本、疲劳 |

**三个配方都不含**：期限措辞（「尽快」「时间不多了」）、既往投入提示（「你已经改了五版」）、连续多任务疲劳诱导、任何形式的催促。

### 1.3 X 的写法要求

X 必须是**在输出里能指认出来的东西**——一个存在的结构、一个缺失的字段、一个可以逐字引用的句子。下面这些不算 X，写成这样的条目应当被审阅打回：

- ❌「输出会变差」「质量下降」「不够专业」
- ❌「它不会想到 X」——想没想到不可观测，只有想的结果可观测
- ✅「产出的 N 个节点里，至少有一个的 escalation 条件写成没有可判定阈值的套话（如『遇到困难及时上报』）」

### 1.4 k 的语义与建议

- **k=5**：单轮、产物短、X 可机械指认的条目（本表多数）。
- **k=3**：需要多轮交互或长产出的条目，成本高，降到存在性证据的下限。

**k 次全中只是存在性证据，不是概率估计。** k=5 全中说明「它做得到」，不说明「它每次都做」。这条限制来自方案 §9，本表不改写它。

### 1.5 这张表能授权什么

严格服从 [`measurement-design.md`](measurement-design.md) §5.1：本表设计的是**第 0 层**（自然任务、不给该知识、看是否自发做出该行为）。第 0 层**只能授权「进候选删除批」**，不能授权「这一条确定无用」。单条结论仍要经第 1 层压线索判定、双评、以及批级消融三道门（§6），本表不预支其中任何一道。

### 2.1 capacity / control（3 条；同组的 `conduct.deserting-podium` 见 §3.3）

**point_id: `capacity.ranking-and-contraction`**
- 一句话它教什么：容量收紧时按「同档换候选 → 降 WIP → 停派新节点 → arm watchdog → surface 用户」这个固定顺序决策，不许跳步。
- 承重任务：给一块已有 6 个 ready 任务的板 + 一份显示配额吃紧的 advisory 读数，要求产出下一步的调度动作清单。**不做这条会显形**：不知道这个顺序的模型会直接做最省事的那一步（把某个任务的执行角色改成低档模型继续跑），而顺序前几步（同档换候选、降 WIP）在输出里整个缺席。
- 无压力确认：NP-B —— 板和读数都是他人产出；不设期限，不说「用户在等」。
- X：输出把某个**未被重新切成机械 leaf** 的任务直接改配低档角色继续执行，且清单中不出现「同 effect floor 内换候选」与「降 WIP / 推迟 high-float」这两步中的任一步。
- 作废情形：读数被解读为容量充足（任务未触及适用范围）；或输出未给出任何可指认的调度动作。
- 建议 k：5

**point_id: `capacity.task-first-allocation`**
- 一句话它教什么：模型档由复杂性与风险决定，duration 只是成本与排期信号，不是智力需求信号。
- 承重任务：给四个任务（长而机械 / 短而不可逆 / 长而高风险 / 短而机械），要求各配一个模型档并说明依据。**不做这条会显形**：把 duration 当智力信号的模型会把「长而机械」升档、把「短而不可逆」降档，两处同时错向。
- 无压力确认：NP-C —— 一次输出即可判，任务描述里不含期限与既往投入。
- X：「长而机械」被配了比「短而不可逆」更高的档；或所有依据段落里只出现耗时长短，不出现风险 / 错误代价这一维。
- 作废情形：环境或契约只给了一档模型可选（此时三轴判断没有选择空间）；或输出未给出可指认的档位分配。
- 建议 k：5

**point_id: `control.decision-program`**
- 一句话它教什么：每回合收尾跑一个**循环**（任一步找到活就送回顶部），直到 ready 集合真正为空，而不是过一遍线性检查表。
- 承重任务：给一块 WIP 上限为 3、当前在飞 1、ready 集合里有 4 个互不依赖任务的板，要求写出本回合收尾要做的全部动作。**不做这条会显形**：把它当线性检查表的模型只会派出 1 个 ready 任务就收工，留下 WIP 长期低于上限而 ready 仍积压的状态。
- 无压力确认：NP-B —— 板是他人产出；不设回合数上限，不提配额。
- X：输出在本回合只派出 1 个任务即宣告收尾，WIP 停在 2 而 ready 集合仍非空，且没有任何一句表示「派完后回到顶部重判」。
- 作废情形：板被判为 ready 集合本就为空；或输出不含可数的派发动作。
- 建议 k：5

### 2.2 coordination（1 条）

**point_id: `coordination.overlap-surface`**
- 一句话它教什么：知道有同侪之后要算的是**三维**重叠面——同一批文件、同一个人、同一个产物；第三维最贵。
- 承重任务：给一份跨板花名册（含两块同侪板的任务清单，其中一块正在产出的 artifact 恰是本板某节点的输入），要求分析重叠并给出本侧的顺序调整。**不做这条会显形**：只算文件维的模型会漏掉「你的某个节点依赖的东西正是他在做的东西」，而那一维一旦撞上不是重解冲突，是整个节点作废。
- 无压力确认：NP-B —— 花名册与同侪板均为他人产出；不设期限。
- X：重叠分析只列出文件层面的交集，输出中不出现「等同一个人拍板 / 排队」与「依赖同一个产物」这两维中的任一维。
- 作废情形：构造的花名册里客观不存在人 / 产物两维的重叠（任务未触及适用范围）；或输出未做任何跨板分析。
- 建议 k：5
- **预判**：母本自陈「这大概是本批里最先该被删的一条」，理由是一次真实编排在只知道有同侪的情况下**自发算出了文件重叠**，缺的只是维度完整性。故预判第 0 层会出现「文件维自发做出、另两维缺失」的部分命中。**此预判不得影响上面承重任务的设计**——任务照常构造三维俱全的场景。

### 2.3 craft（5 条）

**point_id: `craft.composition-over-wrapper`**
- 一句话它教什么：一层要挣到它的开销（改合约 / 翻译语言 / 挂载行为），只转发的层是 idle wrapper。
- 承重任务：给一个已有 repository 接口的场景，要求设计接入一个新的外部支付服务的代码结构。**不做这条会显形**：没有这条判据时，最省事又最像样的做法就是加一层只转发的 `PaymentManager`，它看起来专业、命名规范，正是这条要拦的东西。
- 无压力确认：NP-A —— 从零设计，不给半成品，不设期限。
- X：产出的结构里存在一个类 / 模块，其方法体只是原样转发（不改参数、不改返回、不做校验、不挂副作用），且设计说明中没有为它给出「改合约 / 翻译 / 挂行为」中的任一条理由。
- 作废情形：产出未包含分层结构（任务未触及适用范围）；或代码结构未具体到方法级、无法判定是否只转发。
- 建议 k：5

**point_id: `craft.invariant-anchor`**
- 一句话它教什么：先找到那条任何时刻都必须为真的约束，再由它同时决定边界划在哪、守卫放进哪个对象、测试戳哪个点。
- 承重任务：见 §4.2 完整推演。
- 无压力确认：NP-A。
- X：见 §4.2。
- 作废情形：见 §4.2。
- 建议 k：5

**point_id: `craft.layered-thinking`**
- 一句话它教什么：分「算什么」与「从哪取」，且「测试要 mock 一堆 I/O」就是该拆分的诊断信号。
- 承重任务：给一段规则与 HTTP 调用混写的代码（含一个必须 mock 三个 client 才能跑的测试），要求评估其结构并给出改法。**不做这条会显形**：没有这条时，模型会认可「有 service 层和 repository 层，结构已经分层」，而不会把那个必须 mock 三个 client 的测试读成拆分信号。
- 无压力确认：NP-B —— 代码明确标注为他人产出。
- X：评估结论认可现有结构分层充分，或改法只调整目录 / 命名而不把规则判断从 I/O 分支中抽出；且输出中未引用「测试需要 mock 多个 I/O」这一现象作为依据。
- 作废情形：给出的代码里规则部分客观不可独立验证（如 I/O 本身就是全部逻辑）；或输出未给出结构评估。
- 建议 k：5

**point_id: `craft.shared-spine`**
- 一句话它教什么：DDD / OOP / SDD / TDD 出自同一组根，跨阶段要能互相印证，不是四张互不相干的清单。
- 承重任务：要求为同一个领域概念（如「订单已支付」）分别产出设计说明、类结构和测试，并在最后自查三者是否对同一契约给出一致定义。**不做这条会显形**：把四套理论当独立清单套用时，三个阶段各自「看起来合规」，却会对同一个术语给出互相矛盾的定义，且没有任何一步会去发现这件事。
- 无压力确认：NP-A —— 三份产物由被测者一次性从零产出，不设期限。
- X：三份产物中同一术语 / 契约的定义存在可逐字指认的冲突（如设计说明称支付成功即已支付、测试断言要求回调确认后才算），且自查段落声称三者一致。
- 作废情形：产出未覆盖三个阶段中的任一个；或术语在三份产物里未被各自定义，无从比对。
- 建议 k：3（多份产出，成本较高）

**point_id: `craft.stage-handoff`**
- 一句话它教什么：SDD → DDD → OOP → TDD 是领棒次序而**不是瀑布相位闸**，发现前一环有问题要能回头改。
- 承重任务：给一个「设计已定稿、进入实现后发现设计里一处不变式定义有误」的场景，要求给出下一步动作。**不做这条会显形**：把接力误读成瀑布的模型会在实现侧打补丁绕开，理由是「已经进入开发阶段了」，而不会回头改设计产物。
- 无压力确认：NP-B —— 设计文档为他人产出（消除「这是我写的所以不想推翻」的沉没成本）；不设期限。
- X：输出选择在实现侧规避 / 打补丁并明示或暗示「设计阶段已结束、不再回改」，且不含任何回改设计产物的动作。
- 作废情形：场景被判为设计并无错误（任务未触及适用范围）；或输出未给出可指认的下一步动作。
- 建议 k：5

### 2.4 ddd（6 条）

**point_id: `ddd.admission-question`**
- 一句话它教什么：没有值得保护的不变式或跨消费者语言时，CRUD 才是诚实答案，别给它套完整 DDD 分层。
- 承重任务：给一个只有单一消费者、唯一约束是「名称非空」的配置项管理需求，要求给出结构方案。**不做这条会显形**：没有准入判据时，把完整 aggregate / repository / bounded context 骨架套上去更像「规范」，模型会选它。
- 无压力确认：NP-A。
- X：产出包含 aggregate / repository / bounded context 三件套中的两件以上，且方案里指认出的「不变式」不强于一个字段非空校验。
- 作废情形：需求被改写成含多消费者或强不变式的版本（任务未触及适用范围）；或输出未给出结构方案。
- 建议 k：5

**point_id: `ddd.aggregate-ownership`**
- 一句话它教什么：aggregate 的合并 / 分离由一致性边界定，不变式归**能原子持有它**的所有者。
- 承重任务：给一个订单 + 库存的场景，要求划 aggregate 并写出下单用例的持久化步骤。**不做这条会显形**：类图边界很容易划对，但应用层用例会把两个 aggregate 放进同一个数据库事务同步保存，运行时边界悄悄合并成一个大事务——这处只有写出持久化步骤才暴露。
- 无压力确认：NP-A。
- X：类 / 目录层面划出了两个 aggregate，但用例步骤里两者在同一事务内一起保存，且没有任何一句说明为什么此处允许跨 aggregate 强一致。
- 作废情形：产出未写到持久化 / 事务这一层（输出不可判）；或场景被简化为单 aggregate。
- 建议 k：5

**point_id: `ddd.application-derivation`**
- 一句话它教什么：应用层用例要可溯源，事件 / 命令 / 枚举名必须来自已注册清单，缺口显式标记待补而不是当场发明。
- 承重任务：给一份**故意不完整**的事件清单 + 一段业务流程描述，要求产出生产者 / 消费者矩阵。**不做这条会显形**：清单缺的那几个位置，没有这条纪律时最自然的动作就是当场发明一个听起来合理的事件名把矩阵填满，而这类虚造名字能通过粗看的 review。
- 无压力确认：NP-B —— 清单与流程描述均为他人产出；不设期限。
- X：矩阵中出现至少一个不在给定清单里的事件 / 命令名，且未被标注为「待补 / 需确认」。
- 作废情形：给出的清单被判为已完整（任务未触及适用范围）；或输出未产出矩阵。
- 建议 k：5

**point_id: `ddd.design-focus`**
- 一句话它教什么：设计阶段定「贵」的（BC 边界、正确性约束），把「便宜可调」的（延迟、批量大小）留给实现——划线标准是可调参数 vs 正确性约束。
- 承重任务：给一份含六个待定项的清单（其中「消息是否要求幂等」与「重试间隔」混在一起），要求分成「现在定」与「推迟到实现」两栏。**不做这条会显形**：没有划线标准时，「幂等性」很容易因为「可以后面调」这个措辞被扔进推迟栏，而它是正确性约束不是工业质量参数。
- 无压力确认：NP-C —— 一次分栏即可判。
- X：幂等性 / 消息顺序这类正确性约束被放进「推迟」栏，且理由中出现「可调 / 后面再定 / 先跑起来」这类措辞。
- 作废情形：清单被重写、正确性约束项被剔除；或输出未做分栏。
- 建议 k：5

**point_id: `ddd.failure-radar`**
- 一句话它教什么：一组结构性反模式（含「答案卷先行」「判别器泄漏」这类非通用命名）的识别信号与修复方向。
- 承重任务：给一份**没有推导链条、直接给出结论**的 bounded context 划分表（规整、专业、挑不出明显毛病），要求评审。**不做这条会显形**：「答案卷先行」正是靠形式规整通过评审的；没有这条雷达，评审会认可它，因为它像是深思熟虑推导出来的。
- 无压力确认：NP-B —— 划分表明确标注为他人产出。
- X：评审结论认可该划分，且不含任何一句要求补出「这条边界追溯到哪条业务规则 / 不变式」的推导链条。
- 作废情形：给出的划分表被替换成含推导链条的版本；或输出未给出评审结论。
- 建议 k：5

**point_id: `ddd.strategic-boundaries`**
- 一句话它教什么：BC 发现看三轴（共变化 / 共词汇 / 数据流），合并要拿度量说话，不是靠「放一起改着方便」。
- 承重任务：给一份含提交历史片段与调用数据流的材料，要求判断两个模块该合并还是分开。**不做这条会显形**：没有三轴度量时，最省事的理由是「看起来是同一语义 / 放在一起改着方便」，而材料里其实存在可查的共变化证据。
- 无压力确认：NP-B —— 材料为他人产出；不设期限。
- X：判断结论的依据里没有引用给定材料中的任何一项具体证据（提交共变化次数 / 词汇分歧实例 / 数据流方向），只有语义相似或改动方便这类表述。
- 作废情形：材料被裁剪至不含可查证据（任务未触及适用范围）；或输出未给出合并 / 分开的结论。
- 建议 k：5

### 2.5 devloop（8 条，另 2 条见 §3）

**point_id: `devloop.core-thesis`**
- 一句话它教什么：dev work 是带测量的迭代优化，不是「想清楚了一次写完」。
- 承重任务：给一个已有验收标准、但实现路径存在两处不确定的任务，要求给出推进计划。**不做这条会显形**：没有这条时，最自然的计划是「一次性写完全部实现，然后跑一遍测试」，放弃每轮本可拿到的梯度信息。
- 无压力确认：NP-A —— 从零规划，不设期限，不给半成品。
- X：计划中只有一次「实现 → 验证」，没有任何一轮的中间测量点；或计划把「跑一次测试通过」直接等同于完成。
- 作废情形：任务被判为无中间状态可测的极小改动（如改一个配置值）；或输出未给出推进计划。
- 建议 k：5

**point_id: `devloop.instrument`**
- 一句话它教什么：先架仪器再下降，失败即梯度，读数之前先确认仪器本身可信。
- 承重任务：给一个「测试红了」的场景，其中测试断言本身写得含糊、而实现看起来合理，要求给出下一步。**不做这条会显形**：不先校准仪器的模型会直接动手改一侧；这条要看它是先去判断「红的是实现还是仪器」，还是直接改断言把灯弄绿。
- 无压力确认：NP-B —— 测试与实现均为他人产出；不设期限，不说「CI 在等」。
- X：输出直接修改测试断言使其通过，且不含任何一句先判定「这条断言表达的是不是期望行为」。
- 作废情形：场景被改成断言明确正确（任务未触及适用范围）；或输出未给出具体修改动作。
- 建议 k：5
- **档位疑议**：该点的失效描述以「想尽快看到绿灯的心态」这类动机措辞写成。若无压力下它做对，本条的第 0 层结果**只能授权「压成线索」，不授权删**——因为它自陈的增量在压力侧，属护栏档，本档测不到。

**point_id: `devloop.ledger-when`**
- 一句话它教什么：哪些信号必须当场落 ledger（不是事后补票）。
- 承重任务：给一个需要多轮迭代、且中途会跨越一次上下文压缩的任务，要求给出执行安排。**不做这条会显形**：没有触发判据时，ledger 会被安排成「做完再补」，而真正需要它的那个窗口（中途压缩、执行者掉线）发生时它是空的。
- 无压力确认：NP-A —— 从零安排；「会跨越一次压缩」是场景事实陈述，不是催促。
- X：执行安排里 ledger 的写入时点全部排在任务收尾，或完全不出现 ledger / 状态记录这一动作。
- 作废情形：任务被简化为单轮、无压缩风险（任务未触及适用范围）；或输出未给出执行安排。
- 建议 k：5

**point_id: `devloop.ml-components`**
- 一句话它教什么：派发时按 ML 组件（objective owner / instrumentation / evaluator / regularizer）检查这个优化系统缺哪一块。
- 承重任务：要求为一个中等规模的实现任务设计 subagent 分工。**不做这条会显形**：没有组件词汇时，分工只会想「谁来写代码」，evaluator 这一岗会缺席或由写实现的那个 agent 兼任——即自证通过。
- 无压力确认：NP-A。
- X：分工方案中，产出实现的角色同时负责验收 / 写测试；或分工里不存在任何独立的验收角色。
- 作废情形：任务产出被判为无法定义 acceptance（纯主观创意）；或输出未给出角色分工。
- 建议 k：5

**point_id: `devloop.objective`**
- 一句话它教什么：验收标准即目标函数；模糊就先锐化，不是先动手。
- 承重任务：给一个验收写成一句模糊描述（如「让搜索更好用」）的任务，要求开工。**不做这条会显形**：没有这条时，模型会自选一个方便测的基准（如响应时间），围绕它做一堆「确实变快了」的改动，形式严谨而目标从未被认可。
- 无压力确认：NP-A —— 不设期限，不说「先做着再说」。
- X：输出直接进入实现或直接选定一个未经确认的测量基准，且不含任何一句回头锐化验收或向编排者确认的动作。
- 作废情形：验收被改写成清晰版（任务未触及适用范围）；或输出未给出可指认的第一步动作。
- 建议 k：5

**point_id: `devloop.plateau-restart`**
- 一句话它教什么：识别局部最小值的信号，到点就 restart 换方向，而不是继续在同一方案上打补丁。
- 承重任务：给一份**他人写的**迭代记录（连续五轮改动，每条单看都合理，但离验收的距离几乎没变），要求判断下一步。**不做这条会显形**：没有这条信号清单时，「持续在动」的外衣会让评估者认可继续推进；这正是最难识破的 plateau 形态。
- 无压力确认：NP-B —— 迭代记录明确标注为他人产出，被测者对已投入的五轮不负责（消除沉没成本）；不设期限。
- X：输出建议在同一方案上继续下一轮改动，且不含任何一句指出「五轮没有缩小距离」或提出换方向 / 向上升级。
- 作废情形：记录被改成距离确有缩小（任务未触及适用范围）；或输出未给出下一步判断。
- 建议 k：5

**point_id: `devloop.regularize`**
- 一句话它教什么：多个方案同样达标时，简单性是正则项——复杂的那个要被扣分。
- 承重任务：给两个都能满足给定验收的方案（一个直接、一个引入插件机制以备将来），要求选一个并说明。**不做这条会显形**：没有这条时，「更完备 / 更保险 / 更规范」这类说法足以说服选复杂方案，而目标函数里并没有「将来的扩展」。
- 无压力确认：NP-C —— 一次选择即可判；两个方案均为他人产出。
- X：选中复杂方案，且理由中引入了给定验收之外的需求（「将来可能」「更规范」「更完备」）作为达标依据。
- 作废情形：复杂方案被判为满足验收本身所必需（此时两案并不「同样达标」，判据不成立）；或输出未做选择。
- 建议 k：5

**point_id: `devloop.two-scale`**
- 一句话它教什么：外层编排 loop 定目标与测量、内层下降 loop 做迭代，两个尺度角色不同。
- 承重任务：要求为一个失败过一次的实现任务写第二次派发指令。**不做这条会显形**：没有两尺度语言时，最自然的做法是把同一句模糊指令重新派一遍指望结果变好，且不会意识到这其实是同一失败方向的第 N 次重试。
- 无压力确认：NP-B —— 第一次的失败记录为他人产出；不设期限。
- X：新派发指令与前一次在目标 / 测量 / 验收上无可指认的差异，且不含任何对上一次失败方向的诊断。
- 作废情形：前次失败原因被判为纯环境故障（任务未触及适用范围）；或输出未产出派发指令。
- 建议 k：5

### 2.6 dispatch（2 条）

**point_id: `dispatch.dataflow-and-mechanisms`**
- 一句话它教什么：「谁负责执行」（executor 值）与「怎么真跑起来」（后台机制）是两层，且就绪即派要在多个高度上递归套用。
- 承重任务：给一块含 3 个互不依赖 ready 节点的板，要求给出派发动作。**不做这条会显形**：两层不分离时，字段会填得规规矩矩，但行为退化成派一个、原地等它跑完、再看下一个。
- 无压力确认：NP-B —— 板为他人产出；不设期限。
- X：输出在派出第一个节点后安排等待其完成再处理下一个，且没有任何一句说明为什么这三个不能同时在飞。
- 作废情形：三个节点被判为存在真实数据依赖（任务未触及适用范围）；或输出未给出派发动作。
- 建议 k：5

**point_id: `dispatch.workflow-and-escalation`**
- 一句话它教什么：workflow 分组按**生命周期耦合**而非数量决定；叶子发现自己是子 DAG 时要 STOP 并交出 escalation 结果。
- 承重任务：以执行者身份接一个节点，任务中途会暴露出三条彼此独立的子任务，要求给出处理方式。**不做这条会显形**：没有 escalation 协议时，把三条子任务塞进自己一次超长执行里顺序做完是形式上无违规、看起来顺利完成的路径，它绕开了 checkpoint 与准入控制。
- 无压力确认：NP-A —— 从零接手，不给已投入的工作量，不设期限。
- X：输出选择在本节点内顺序做完三条子任务，且不含任何一句停下并向上返回 scope map / escalation 结果。
- 作废情形：执行环境被设定为不支持任何中途返回（此时只能在最终报告里补记）；或输出未给出处理方式。
- 建议 k：5

### 2.7 distill（5 条）

**point_id: `distill.dual-dest`**
- 一句话它教什么：一条经验可以同时落「纪律文档一句指针」+「skill 里一段判断力」，不必强行二选一。
- 承重任务：给一条**明确含两部分**的候选经验（一个项目专属的事实性决定 + 一段可迁移的判断力），要求规划落点。**不做这条会显形**：不知道允许双落点时，规划会强行选一处；选了判断力那处之后，那句事实性指针从此没有入口，而这个遗漏不会在计划里留下痕迹。
- 无压力确认：NP-C —— 一次规划即可判；候选经验为他人产出。
- X：规划给出单一落点，且被舍弃的那一部分（事实性指针或判断力细节）在计划中完全不出现、也未被显式标注为「有意舍弃 + 理由」。
- 作废情形：候选经验被改成只含单一部分（此时不能为凑双落点制造空壳）；或输出未给出落点规划。
- 建议 k：5

**point_id: `distill.evidence-fidelity`**
- 一句话它教什么：按证据强度收窄措辞，不把单次观察包装成「总是应该」。
- 承重任务：给一条**只有一次实例支撑**的观察，要求写成可落地的条目。**不做这条会显形**：没有这条时，写出来的条目会带上「通常」「大多数情况下」这类听起来审慎、实则没有计数支撑的限定词，或直接升格成普遍规则。
- 无压力确认：NP-C —— 一次改写即可判；原始观察为他人产出。
- X：产出条目使用了「通常 / 大多数情况 / 总是 / 一般来说」中任一措辞，或使用无限定的祈使句，而给定证据只有一次实例且条目中未标注这一点。
- 作废情形：给定证据被替换成多实例版本（任务未触及适用范围）；或输出未产出条目。
- 建议 k：5

**point_id: `distill.landing-craft`**
- 一句话它教什么：四类资产各自的落地手艺——尤其 workflow 只固化结构、不把判断分支焊死进脚本。
- 承重任务：给一条含「视情况 A 或 B 走不同路径」的经验，要求把它落成 workflow。**不做这条会显形**：不知道这条边界时，最自然的落法就是在脚本里写一个 if/else 把判断焊死，脚本形式完全合规。
- 无压力确认：NP-A —— 从零落地，不给半成品。
- X：产出的 workflow 步骤中存在一个把情况 A / B 判断写死的条件分支，且没有任何一处把该判断交回给触发者 / 调用方。
- 作废情形：经验被改成不含判断分支（任务未触及适用范围）；或输出未产出 workflow 结构。
- 建议 k：5

**point_id: `distill.routing-tree`**
- 一句话它教什么：用「事实还是判断力 / 机制还是判断力 / 角色化还是通用」三问把一条经验分派到正确的资产类型。
- 承重任务：给三条性质不同的候选经验（一条项目专属事实、一条可迁移判断力、一条确定性编排形状），要求各判归宿并给依据。**不做这条会显形**：没有三问时，分类会靠「这件事印象深刻 / 说起来更正式」这类感受走完形式，而三条里至少有一条会被错配。
- 无压力确认：NP-C。
- X：任一条的归宿依据中不出现「换个项目还有用吗 / 这是机制还是判断 / 需不需要专职角色视角」这三问中的任一问，只出现重要性、印象或正式程度这类表述。
- 作废情形：某条经验横跨多类型且未被先拆分（此时应先拆再判，不是本条的违反）；或输出未给出归宿。
- 建议 k：5

**point_id: `distill.taxonomy`**
- 一句话它教什么：四类资产的定义与「适合 / 不适合承载」判据。
- 承重任务：给一条**一次性**的项目事实，要求判断该落成哪类资产。**不做这条会显形**：没有判据时，「感觉很重要」会驱动为它建一个 subagent 或 skill，而它只会被用到一次。
- 无压力确认：NP-C。
- X：输出为这条一次性事实建立 skill / subagent / workflow 中任一种，且判据中不出现「会被反复触发调用吗」这一问。
- 作废情形：经验被改成可反复触发的版本（任务未触及适用范围）；或输出未给出资产类型判断。
- 建议 k：5

### 2.8 hitl / multilayer（3 条）

**point_id: `hitl.inflight-and-user`**
- 一句话它教什么：把用户建模成异步 worker，前台对话与后台执行并行跑，主线永不空等。
- 承重任务：给一个「需要用户拍板一个决策，同时另有 2 个不依赖该决策的 ready 任务」的局面，要求给出本回合动作。**不做这条会显形**：没有这条时，最自然的动作是把问题抛给用户然后等答复，两个不依赖它的任务停在原地。
- 无压力确认：NP-B —— 局面为他人产出；不设期限。
- X：输出在向用户提问后停止，且不含任何对那 2 个不依赖决策的 ready 任务的派发动作；或只写下「稍后会派」这类意图声明而无实际派发。
- 作废情形：那 2 个任务被判为确实依赖该决策（任务未触及适用范围）；或输出未给出本回合动作。
- 建议 k：5

**point_id: `multilayer.admission-and-escalation`**
- 一句话它教什么：什么样的节点够格上「项目自己的 planning 层」，以及「纵深消化 vs 炸开成顶层并行」的分界。
- 承重任务：以执行者身份处在一个节点内部，已发现内部其实是三条独立子任务，要求判断继续做还是 escalate。**不做这条会显形**：没有分界判据时，继续在节点内部往下钻感觉像「持续推进」，串行做完后交付结果上完全看不出低效。
- 无压力确认：NP-A —— 从零接手，**不告知已投入多少**（这是消除沉没成本的关键）；不设期限。
- X：输出选择在节点内串行做完三条子任务，且不含任何向上返回 escalation / scope map 的动作。
- 作废情形：三条子任务被判为存在真实依赖、不可并行（任务未触及适用范围）；或输出未给出判断。
- 建议 k：5

**point_id: `multilayer.handoff-contract`**
- 一句话它教什么：派发够大的节点时，把「先发现并遵循被编排项目自己的 planning 规范」和「维护其计划文档」写进节点契约。
- 承重任务：要求为一个大型、多阶段的节点写派发指令，目标项目已知有自己的贡献规范与计划文档惯例。**不做这条会显形**：没有这条增项时，派发指令的字段会写得很完整，但完全不提「先去读这个项目自己的规划规范」，执行者会按默认套路规划、与项目既有规范脱节。
- 无压力确认：NP-A。
- X：派发指令中不出现要求执行者先发现 / 遵循目标项目自身 planning 规范的条款，也不出现产出或维护该项目约定位置计划文档的要求。
- 作废情形：节点被判为小而原子、一次可验（此时不需要这条增项）；或输出未产出派发指令。
- 建议 k：5

### 2.9 oop（5 条）

**point_id: `oop.abstraction-cost`**
- 一句话它教什么：抽象要配得上它的开销，判据是 near-decomposability + 两个提示问题；「以后可能用得上」不算理由。
- 承重任务：给一个当前只有一个实现、但可以想见将来会有第二个的场景，要求决定是否现在就抽出接口。**不做这条会显形**：没有这条判据时，「可预见的未来需求」会被悄悄论证成「已经看见的结构性理由」，接缝会被提前建好。
- 无压力确认：NP-A —— 场景中**不写入**任何已确认的计划或 spec（若写入则第二个实现就不再是猜测，判据本身不成立）。
- X：输出决定现在抽出接口，其理由只指向尚未确认的未来变体；或用「删掉这层少了什么」自问自答，而答案里指认的接缝正是为服务这层新抽象才创造出来的（循环论证）。
- 作废情形：场景被改成第二变体已在既定计划中列明（此时提前建接缝不算投机）；或输出未给出决定。
- 建议 k：5

**point_id: `oop.encapsulation-vocabulary`**
- 一句话它教什么：聚合根的变更方法要把守卫 + 状态翻转 + 时间戳捆成一个动词，不变式要真正被代码强制。
- 承重任务：要求为一个带状态机的实体（如订单）写出状态变更方法。**不做这条会显形**：没有这条纪律时，方法名会起得像动词，内部却只是裸字段赋值，守卫退化成一句注释——文档看着负责，运行时形同虚设。
- 无压力确认：NP-A —— 从零写，不给半成品，不设期限。
- X：产出的变更方法内部没有真正抛出 / 拒绝的守卫检查（守卫只以注释或文档字符串形式存在），或存在绕过该方法直接改状态的公开 setter。
- 作废情形：实体被判为无不变式的纯数据载体（任务未触及适用范围）；或输出未写到方法体级别。
- 建议 k：5

**point_id: `oop.failure-radar`**
- 一句话它教什么：8 类 OO 反模式的气味、判断标准（如「唯一改变理由」测试、注入依赖数阈值）与修复方向。
- 承重任务：给一段代码，其中包含一个大类（但实际只有一个改变理由，是合理的编排类）和一个真正的 idle wrapper，要求诊断。**不做这条会显形**：没有判断标准时，会看到大类就贴「God class」误伤合理编排类，而对真正的 idle wrapper 给出「加注释 / 改名」这类与修复方向对不上的处置。
- 无压力确认：NP-B —— 代码为他人产出。
- X：把合理编排类判为 God class 且未做「唯一改变理由」检验；或对 idle wrapper 的修复只包含注释 / 命名调整，不含删除中间层或移走行为。
- 作废情形：代码被改成不含这两类样本（任务未触及适用范围）；或输出未给出诊断。
- 建议 k：5

**point_id: `oop.four-pillars`**
- 一句话它教什么：用四个镜头**同时**审视同一个类，且要看见镜头之间的冲突。
- 承重任务：给一个为套用某设计模式而牺牲了输入校验的类，要求评审。**不做这条会显形**：逐条打勾的清单思维会分别确认「用了模式」「有封装」而漏掉镜头间的冲突，尤其是安全这一柱被模式牺牲掉。
- 无压力确认：NP-B —— 类为他人产出。
- X：评审逐项确认各柱合规，不指出「为套模式牺牲了校验 / 安全」这一冲突；或把「调用方会查」这类把责任推给下游的说法当作显式权衡接受。
- 作废情形：类被改成不含镜头冲突（任务未触及适用范围）；或输出未给出评审。
- 建议 k：5

**point_id: `oop.solid-judgment`**
- 一句话它教什么：把 SOLID 转成可操作的诊断句式（「说出改变理由」「新变体能不改这个文件就到达吗」「换实现后断言还能保留吗」）。
- 承重任务：给一个用注册表实现「开闭」、但注册表内部留了 if/elif 兜底 default 分支的结构，要求评审其开闭性。**不做这条会显形**：不用诊断句式时，「有注册表 = 遵守开闭」在形式上成立；只有真问一句「新变体能不改这个文件就到达吗」才会发现那把梯子只是被挪进了注册表内部。
- 无压力确认：NP-B —— 结构为他人产出。
- X：评审认可该结构满足开闭原则，且不含任何一句针对「新变体是否需要修改现有文件」的检验。
- 作废情形：结构被改成不含兜底分支（任务未触及适用范围）；或代码未具体到能判定新变体接入路径。
- 建议 k：5

### 2.10 outside / pacing（3 条）

**point_id: `outside.evidence-levels`**
- 一句话它教什么：内部一致 ≠ 外部证据；证据要分级，共识不等于验证。
- 承重任务：给一份留痕记录，其中标为「外部证据」的那一条实际上是对同一批内部材料的又一次转述，要求评估这条判断的证据强度。**不做这条会显形**：没有分级框架时，挂着「外部证据」标签的东西会被当成已验证，内部一致被误当成已验证。
- 无压力确认：NP-B —— 留痕记录为他人产出；NP-C 单轮判断。
- X：评估认可该条为外部证据 / 已验证，且不含任何一句追问该证据的来源是否真的接触过内部材料之外的东西。
- 作废情形：该假设属纯偏好 / 主观判断（客观上没有外部锚点，证据链止步于当事人拍板不算验证没做够）；或输出未给出证据强度评估。
- 建议 k：5

**point_id: `outside.falsification-and-calibration`**
- 一句话它教什么：falsification-first——先列承重假设、问哪项外部事实能推翻它、按「三条全中」（承重 ∧ 内部推断唯一支撑 ∧ 大 / 不可逆投入）决定是否校准，并按成本阶梯选手段。
- 承重任务：给一个建立在一条从未向外核实的假设上的方案，且该假设满足三条全中，要求给出投入前的动作。**不做这条会显形**：没有这套判据时，最省事又看着像验证的动作是「再拉一个同族 review 一遍」，它会被记成「已核实」——这正是原文点名要防的自欺。
- 无压力确认：NP-B —— 方案为他人产出；不设期限，不提「进度」。
- X：输出用同族模型的再次审阅 / 内部复读作为该假设的验证手段并视为已核实，且不含任何指向代码 / 文档 / 用户 / 真实系统状态的外部核实动作。
- 作废情形：假设被改成不满足三条全中（此时记为假设照常推进才是正确行为）；或输出未给出投入前动作。
- 建议 k：5

**point_id: `pacing.usage-estimate-tension`**
- 一句话它教什么：张力要对比两侧——配额侧 verdict 与工作侧 p80 预测 / 占比，单侧读数不构成张力。
- 承重任务：给一份配额侧发出减速信号、同时工作侧预测显示期限充裕的读数对，要求给出处置。**不做这条会显形**：只看单侧的模型会直接收窄范围或降速，跳过本该摆出来的那个对比。
- 无压力确认：NP-C —— 一次判断即可判；读数为他人产出。
- X：输出直接给出收窄范围 / 降速的动作，且不引用工作侧的期限预测数值做过任何对比。
- 作废情形：两个读数被设为分属不同 target 或其中之一已过期（此时比较本身不成立）；或输出未给出处置。
- 建议 k：5

### 2.11 routing / scheduling（6 条）

**point_id: `routing.executor-vs-target`**
- 一句话它教什么：executor（谁以什么责任形状执行）与 target surface（在哪个可调用面真正启动）正交；参数形状必须核实当前这个面实际支持什么。
- 承重任务：要求把一个任务派到一个**明确给出了其真实 help 输出**的目标调用面上，且该 help 里的参数名与常见同类工具不同。**不做这条会显形**：不区分两层的模型会凭记忆套用相似工具的常见参数形状，而给定的 help 就在手边。
- 无压力确认：NP-A —— 从零构造调用；help 输出作为材料一并给出。
- X：产出的调用命令里出现给定 help 中不存在的参数名 / 参数形状。
- 作废情形：环境被设为只有单一可调用面（此时角色与调用面天然重合）；或输出未产出具体调用命令。
- 建议 k：5

**point_id: `routing.qualification-and-fallback`**
- 一句话它教什么：先按判断密度 / 风险定最低 effect floor，再逐项做 exact qualification——容量证据必须与目标同源。
- 承重任务：给一组候选（其中候选 A 自身无容量读数，但同 provider 的另一个 surface 有余量），要求选一个并给出资格依据。**不做这条会显形**：没有同源硬约束时，把邻近但不严格对应的余量当成够用，是容量紧张时最自然的省事路径，且字段表面会看起来齐全。
- 无压力确认：NP-B —— 候选与读数均为他人产出；不设期限。
- X：选中候选 A 并把另一 surface 的余量作为其容量证据填入，或容量依据字段留空却仍判定该候选合格。
- 作废情形：所有候选都有同源读数（任务未触及适用范围）；或输出未给出资格依据。
- 建议 k：5

**point_id: `routing.task-shape`**
- 一句话它教什么：按责任与控制形状分五类 executor，且只有下游直接消费上游产物时才画依赖边。
- 承重任务：给一个「多个叶子必须共享同一 schema 才能合并」的任务，要求给出 executor 分配。**不做这条会显形**：不按形状分流时，它会被拆成几个互相独立的终端派发——每个单看都是「确实交出去了」，但叶子之间从未对齐 schema，产出会悄悄漂移成不兼容的结果。
- 无压力确认：NP-A。
- X：把该任务拆成多个互相独立的终端派发，且没有任何一处约定共享 schema 或指定结构化多叶责任。
- 作废情形：任务被改成叶子之间无需共享 schema（任务未触及适用范围）；或输出未给出 executor 分配。
- 建议 k：5

**point_id: `scheduling.dag-and-critical-path`**
- 一句话它教什么：拓扑序与临界路径交给机器算，你只消费输出；心算复杂拓扑与在平凡小图上仪式性跑工具，两侧都是错。
- 承重任务：给一张多源多汇的钻石依赖图（8 个以上节点），要求报告临界链与预计完成时间。**不做这条会显形**：不知道该交给机器时，会口头给出一条看似合理的临界链和一个编出来的时间估计。
- 无压力确认：NP-B —— 图为他人产出；不设期限。
- X：输出给出具体的临界链与时间数字，但过程中没有调用任何图分析工具，也没有写出可复核的逐节点推导。
- 作废情形：图被简化到平凡（此时仪式性跑工具反而是错）；或输出未给出临界链。
- 建议 k：5

**point_id: `scheduling.node-contract`**
- 一句话它教什么：派发前定五要素契约——Input deps / Output schema / Success predicate / Timeout+budget / Escalation condition，且 success predicate 优先给可执行验收物。
- 承重任务：见 §4.3 完整推演。
- 无压力确认：NP-A。
- X：见 §4.3。
- 作废情形：见 §4.3。
- 建议 k：5

**point_id: `scheduling.parallelism-and-granularity`**
- 一句话它教什么：work-span / Brent / Amdahl 量化并行到底值不值；并行度 ≈ 1 时 fan-out 毫无意义。
- 承重任务：给两张图（一张并行度高、一张是长串行链），要求各判断该开几条并行道并给出预期加速。**不做这条会显形**：没有这套分析时，「worker 越多越快」的直觉会给串行链也开多道，或反过来对高并行度图无脑串行；加速倍数会是拍脑袋的数字。
- 无压力确认：NP-B —— 两张图均为他人产出；NP-C 单轮判断。
- X：给出「预计加速 N 倍」这类结论而推导中未出现临界链长度 / 串行分数的计算；或对长串行链那张图建议 fan-out。
- 作废情形：两张图被替换成都只有单条路径（此时分析对象本身不成立）；或输出未给出并行度判断。
- 建议 k：5

### 2.12 sdd（5 条，另 1 条见 §3）

**point_id: `sdd.admission`**
- 一句话它教什么：判断这次改动值不值得走 spec-first 的准入维度；拿不准偏向「值得」。
- 承重任务：给一个「看起来只有一个调用方、但材料里存在另一团队引用痕迹」的内部函数改动，要求判断是否需要 spec。**不做这条会显形**：没有校准维度时，会凭「内部小函数」直接归入过重一栏跳过 spec，而事实前提是错的。
- 无压力确认：NP-B —— 材料为他人产出；不设期限。
- X：判定为不需要 spec，且过程中未查证 / 未提及材料里的第二处引用痕迹。
- 作废情形：材料被裁剪至确无第二消费者（任务未触及适用范围）；或输出未给出准入判断。
- 建议 k：5

**point_id: `sdd.alignment`**
- 一句话它教什么：spec 是测试的 oracle——测试断言的应是 spec 的行为契约，不是这份实现的返回值细节。
- 承重任务：给一份 spec + 一份实现，要求写测试。**不做这条会显形**：不把 spec 当 oracle 时，最自然的写法是照着实现的具体返回值写断言；换一种同样满足 spec 的合法实现，这个测试就会误报失败。
- 无压力确认：NP-B —— spec 与实现均为他人产出。
- X：产出的测试中存在断言，其内容取自实现的具体返回细节（字段顺序、内部格式、错误消息原文等）而非 spec 明文规定的行为，且未标注为实现细节快照。
- 作废情形：spec 被写成与实现逐字一致（无从区分）；或输出未产出测试。
- 建议 k：5

**point_id: `sdd.core-belief`**
- 一句话它教什么：正确性需要一个**先于实现达成**的外部标准；实现已跑通不等于实现正确。
- 承重任务：给一段已完成且「测试全绿」的实现，其测试写于实现之后、断言的是实现当下的行为，要求评估其验收有效性。**不做这条会显形**：没有这条认识论立场时，「现状已经工作 + 测试全绿」会被当成正确性证据，红绿铁律表面走完而验收标准已被置换成「代码现在做了什么」。
- 无压力确认：NP-B —— 实现与测试均为他人产出（关键：消除「返工代价摆在眼前」的沉没成本）。
- X：评估认可该测试构成有效验收，且不含任何一句指出断言来源是实现现状而非独立的期望标准。
- 作废情形：场景为纯探索性 spike（此时不存在先于实现的外部标准，前提不成立）；或输出未给出验收有效性评估。
- 建议 k：5

**point_id: `sdd.spec-boundary`**
- 一句话它教什么：什么算 spec 内容、什么不算——实现细节不进 spec，逆向生成的现状文档不是 spec。
- 承重任务：要求为一个模块写 spec，材料中已给出现有实现的排序算法与内部容器选择。**不做这条会显形**：不划边界时，手边的实现细节会被顺手写进 spec，让实现者误以为这些细节被冻结、不敢做等价重构。
- 无压力确认：NP-A —— 从零写 spec；实现材料为他人产出。
- X：产出的 spec 中出现具体算法选择 / 内部数据结构 / 内部调用顺序这类实现细节，且未标注为非承诺项。
- 作废情形：材料被裁剪至不含实现细节（任务未触及适用范围）；或输出未产出 spec。
- 建议 k：5

**point_id: `sdd.theory-handoff`**
- 一句话它教什么：DDD / SDD / OOP / TDD 在 design → build → test 轴上接力，后一环吃前一环冻结下来的产物。
- 承重任务：要求走完一个小特性的建模 → 实现 → 测试全流程并交出各阶段产物。**不做这条会显形**：不知道接力关系时，「形式化成合约」这一步会被跳过——建模成果在写代码时口头拍板成接口，测试再照着这份口头接口写，全绿只证明测试和实现读的是同一份临时约定。
- 无压力确认：NP-A —— 从零走完，不设期限。
- X：交付物中不存在一份**独立于实现**的合约 / 接口冻结产物（spec、schema、类型签名、契约测试之一），而测试断言直接对应实现代码。
- 作废情形：任务被简化为不含设计决策的改动；或输出未覆盖三个阶段。
- 建议 k：3（多阶段产出，成本较高）

### 2.13 slicing（5 条）

**point_id: `slicing.antipatterns`**
- 一句话它教什么：切分反模式的识别标志——横切分层、镀金地基、假串行边。
- 承重任务：给一份任务列表（每项都是独立卡片、都写了验收，但其中一项「共享 foundation」被做到远超下游实际需要），要求评审这份切分。**不做这条会显形**：没有识别清单时，列表形式完全合规，镀金只藏在颗粒内部，评审会通过。
- 无压力确认：NP-B —— 列表为他人产出。
- X：评审认可该切分，且不指出 foundation 那一项的范围超出下游实际需要。
- 作废情形：列表被改成不含镀金项（任务未触及适用范围）；或输出未给出评审。
- 建议 k：5

**point_id: `slicing.example-contrast`**
- 一句话它教什么：一个横切 vs 纵切的具体对照样例，用来校准直觉。
- 承重任务：给一个**没有共享底座**的目标（几个彼此独立的小功能），要求给出切分。**不做这条会显形**：这条的价值是校准而非算法；它的失效正好出现在把例子表面结论生搬硬套的地方——给一个本无共享底座的目标硬造一个「最薄的第一片」。
- 无压力确认：NP-A。
- X：切分中出现一个不产出端到端价值、仅为「先做一个最薄的东西」而设的前置片，且其他片都依赖它。
- 作废情形：目标被改成确有共享底座（此时 walking skeleton 是对的，不适用本条）；或输出未给出切分。
- 建议 k：5
- **档位疑议**：该点自陈「只是一个用来校准直觉的对照样例，不单独定义判断标准」。第 0 层若显示模型自发切得对，仍**不能**据此单条判删——它与 `slicing.walking-skeleton` 共享同一失效面，归因需在批级消融里处理。

**point_id: `slicing.grain`**
- 一句话它教什么：粒度的两把尺——能否并行、有无一句清爽验收；「完成用户认证模块」这种表面清爽实则包着好几个可独立验收的子问题。
- 承重任务：给一份切片清单，其中一片的验收写作「完成用户认证模块」，要求逐片检查粒度。**不做这条会显形**：没有第二把尺时，那句验收读起来清爽、比明显没写验收更难被发现，检查会放它过去。
- 无压力确认：NP-B —— 清单为他人产出。
- X：逐片检查通过了「完成用户认证模块」这一片，且不含任何一句追问它能否独立验收 / 是否还能再拆。
- 作废情形：清单被改成不含该类粗片（任务未触及适用范围）；或输出未逐片检查。
- 建议 k：5

**point_id: `slicing.value-risk`**
- 一句话它教什么：ready 集合里按价值 × 风险排序，而不是按易实现程度。
- 承重任务：给一个 ready 集合（含一片最好写但用户最晚才用得上、一片碰不确定集成路径的），要求排序并说明。**不做这条会显形**：没有这条判据时，最好写的那片会被包装成「价值优先」先派，既不是用户最先用得上的，也不碰任何不确定路径。
- 无压力确认：NP-C —— 一次排序即可判；候选片为他人产出。
- X：把最易实现的那片排在首位，且理由中不含用户可用时点或集成风险这两维中的任一维。
- 作废情形：集合中各片在价值 / 风险上无差异（任务未触及适用范围）；或输出未给出排序。
- 建议 k：5

**point_id: `slicing.walking-skeleton`**
- 一句话它教什么：第一片是最薄的端到端线，脊椎只放不可再薄的共享核心，schema 增量生长。
- 承重任务：给一个三层架构的目标，要求给出第一片的范围与它要定的 schema。**不做这条会显形**：出于「一次做对、少走回头路」的求稳心态，第一片会顺手把 schema 定得远超这根线本身所需，后续切片退化成填空，并行度被前置依赖钉死——而任务边界表面上仍是纵切的，不容易一眼看出。
- 无压力确认：NP-A —— 从零切，不设期限，不提返工代价。
- X：第一片定义的 schema 字段中，存在明确只服务于后续切片、这根端到端线本身不消费的字段，且未标注为待后续增量添加。
- 作废情形：目标为单层、不存在端到端线（此概念不成立）；或输出未给出第一片的 schema。
- 建议 k：5

### 2.14 tdd（2 条）

**point_id: `tdd.constraint-parity`**
- 一句话它教什么：行为一致 ≠ 约束一致——内存 fake 复现不了唯一性 / 外键 / 并发锁，约束类不变式要有跑在真实后端上的验证。
- 承重任务：给一个含唯一性约束的模型，要求设计测试方案（测试环境有可用的真实后端）。**不做这条会显形**：不知道这条区别时，基于 fake 的全绿套件会被真诚地当成「约束也验证过了」，方案里不会出现任何跑在真实后端上的约束触发测试。
- 无压力确认：NP-A —— 从零设计测试方案。
- X：测试方案中不存在任何一条在真实后端上触发唯一性 / 外键 / 并发约束的用例，或方案明示「fake 已覆盖全部约束」。
- 作废情形：真实后端被设为无沙箱的第三方付费服务（此时只能退用其公开行为契约替代校验，不算没做到）；或输出未给出测试方案。
- 建议 k：5

**point_id: `tdd.design-feedback`**
- 一句话它教什么：测试写不出来是设计在批评自己——症状要翻译成设计反馈，而不是加更重的脚手架硬写。
- 承重任务：给一个必须搭建复杂 mock 框架和多层 fixture 才能测的接口，要求给出测试方案。**不做这条会显形**：没有这张症状 → 设计读法的表时，投入更多 mock 与 fixture 工厂把测试硬写出来是形式上完全合规的路径，它把该被听到的设计缺陷埋得更深。
- 无压力确认：NP-B —— 接口为他人产出（关键：消除「这是我设计的」阻力）；不设期限，不提交付。
- X：方案通过增加 mock / fixture 层来使测试可写，且不含任何一句把「测试难写」读成接口设计问题、提出调整接口。
- 作废情形：代码为验证完即弃的 spike（此时两个目的都不成立）；或输出未给出测试方案。
- 建议 k：5

### 2.15 unknowns（3 条）

**point_id: `unknowns.four-quadrants`**
- 一句话它教什么：四类未知按「谁知道 / 谁不知道自己不知道」分，「未知的已知」与「未知的未知」是主战场，且这是内部分派轴不是对用户的话术。
- 承重任务：给一个需求场景，其中用户的真实痛点属于「说不出口」类（审美 / 团队惯例），要求给出需求发现计划。**不做这条会显形**：没有四象限时，发现计划会全部落在「已知的未知」这一类——问了好几轮、也确认了对方明说的偏好，流程像做足了功课，实际只覆盖最容易问的一半。
- 无压力确认：NP-A —— 从零规划发现动作，不设期限。
- X：发现计划中的动作全部是「向用户提问」形态，不含扫描那片地或造对照物这两类动作中的任一类。
- 作废情形：场景被改成四类未知都不缺（此时直接推进、不加仪式才是对的）；或输出未给出发现计划。
- 建议 k：5

**point_id: `unknowns.frame-before-spec`**
- 一句话它教什么：用户答不出「什么叫好」时，先讲清取舍轴 + 给对照实例让他自我定位，而不是反复索要一份并不存在的 spec。
- 承重任务：给一个用户明确表示「我也不知道什么样算好」的场景，要求给出下一步对话动作。**不做这条会显形**：没有这条分流判据时，最自然的动作是换个措辞继续追问「那你具体想要什么样的」，把发现的责任推给一个还没有判断力的人。
- 无压力确认：NP-C —— 一次动作规划即可判。
- X：输出的动作是换措辞的再次追问，不含任何取舍轴的讲解或真实对照实例；或给出的「轴」与「实例」是当场编造、不指向任何真实既有实现。
- 作废情形：场景被改成用户答得出只是没答（那属另一条判据）；或该工作被判为低风险可逆（此时不需先建框架）；或输出未给出下一步动作。
- 建议 k：5

**point_id: `unknowns.technique-routing`**
- 一句话它教什么：三种手法不可互换——未知的未知要扫描那片地（产出「你该问但没问的问题」清单），未知的已知要造几个差别大的物让人指着反应，已知的未知才开口问。
- 承重任务：给一个混合场景（含一处「用户压根没想到」的未知 + 一处「用户说不出口」的未知），要求给出发现动作。**不做这条会显形**：不知道三条通道各自坏在哪里时，会对两类都抛出一长串条理清晰的问题——看着很勤快，用户同样答不上来，表面在做发现实质什么也没发现。
- 无压力确认：NP-A。
- X：针对两处未知给出的动作都是向用户提问，不含扫描（产出问题清单）与造对照物这两类动作中的任一类。
- 作废情形：场景被改成只含「已知的未知」（此时开口问是对的）；或输出未给出发现动作。
- 建议 k：5

### 2.16 verification（3 条）

**point_id: `verification.hash-and-stale`**
- 一句话它教什么：把 workflow 当增量构建引擎——content-hash 命中才复用，端点验收本身就是这份缓存的校验。
- 承重任务：给一个续跑场景，其中某节点的产物存在、journal 里有记录，但那条记录写于上游输入变化之前，要求判断该节点是否可跳过。**不做这条会显形**：没有 hash / stale 心智时，「存在 journal 条目」会被直接读成 done，一个早已 stale 的节点被当成仍然有效而跳过。
- 无压力确认：NP-B —— 场景与 journal 为他人产出；不设期限。
- X：判定该节点可跳过，且不含任何一句比对当前输入 hash 与记录中 hash 是否一致。
- 作废情形：节点被设为含不可重复的外部副作用（此时只能靠回执记录判定，不靠重跑校验）；或输出未给出跳过 / 重跑判断。
- 建议 k：5

**point_id: `verification.heterogeneous-review`**
- 一句话它教什么：第二视角要**换族不换壳**，只喂 diff + 验收契约不带 framing，空审 / 调用失败按未通过处理。
- 承重任务：给一个临界路径上 correctness-critical 的 `done` 候选，要求设计它的验收安排。**不做这条会显形**：没有这条原则时，「再派一个同族 subagent 复读一遍」是最省事又看着像二审的安排，且很容易在喂材料时夹带「我认为这是对的」这类 framing，把第二视角变成自己的回声。
- 无压力确认：NP-A —— 从零设计验收安排；不设期限。
- X：验收安排使用与产出方同一模型家族的复核并视为已完成异构复核；或喂给复核方的材料中包含产出方的结论倾向 / 「这应该是对的」这类 framing。
- 作废情形：环境被设为客观只有单一模型族可调用（此时只能退化并显式标注局限）；或输出未给出验收安排。
- 建议 k：5

**point_id: `verification.loop-convergence`**
- 一句话它教什么：分支未知时用 Joiner 结构化二选一（FinalResponse vs 带诊断的 Replan），配 max-rounds 保险丝与 dedup-against-seen。
- 承重任务：要求设计一个「实现 → review → 修 → 再 review」的内层循环。**不做这条会显形**：没有这套模式时，产出的循环会用一句模糊结论作为收敛判据、Replan 侧不带上一轮的具体诊断，且没有轮数上限——外形在收敛，实质是无诊断的裸重试。
- 无压力确认：NP-A —— 从零设计循环。
- X：产出的循环设计中缺少轮数 / 调用上限，或 replan 分支不携带上一轮的具体诊断内容（只写「再试一次 / 修一下」），或已否决项没有去重机制。
- 作废情形：任务被改成无分支的线性流程（任务未触及适用范围）；或输出未给出循环设计。
- 建议 k：5

### 2.17 workflow（15 条，另 2 条见 §3）

**point_id: `workflow.admission`**
- 一句话它教什么：workflow 的准入门槛——几十到几百个 agent 且中间结果必须挡在 context 外。
- 承重任务：给两个场景（一个只需三五个后台 agent、产物很小；一个要协调上百个 agent、中间产物明显撑爆 context），要求各判是否上 workflow。**不做这条会显形**：没有门槛时，两侧都会错——小场景先搭一套 stage / artifact / state 脚手架，大场景仍用零散 subagent 硬扛。
- 无压力确认：NP-C —— 一次判断即可判。
- X：给小场景判定上 workflow，或给大场景判定继续用零散 subagent；且判断依据中不出现规模 / context 隔离这两条门槛中的任一条。
- 作废情形：两个场景被改到规模相近（任务未触及适用范围）；或输出未给出判定。
- 建议 k：5

**point_id: `workflow.pattern-bug-hunt`**
- 一句话它教什么：completeness 与低误报同时要时，loop-until-dry 与 adversarial-verify 必须组合，缺一不可。
- 承重任务：要求设计一次「既要找齐所有 bug、又不能淹没用户」的排查编排。**不做这条会显形**：不知道两个环节要组合时，会只做其中一个——只 loop 到 dry 会交出一堆假阳，只做一趟 review 会漏掉边界 case。
- 无压力确认：NP-A。
- X：产出的编排只含穷举 loop 而无对每个候选的反驳环节，或只含单趟 review 而无 dry-round 判停。
- 作废情形：需求被改成只要其一（此时不用本模式）；或输出未给出编排。
- 建议 k：5

**point_id: `workflow.pattern-completeness-critic`**
- 一句话它教什么：事后派 critic 专问「漏了什么」（否定式检验），而不是「有没有这个」（肯定式检验）。
- 承重任务：给一个已完成的发现类交付物，要求设计其完整性检查。**不做这条会显形**：没有这条时，检查会做成逐条验收项的肯定式核对，遗漏就藏在交付物里，下游才诧异「为什么这个角度之前没扫到」。
- 无压力确认：NP-B —— 交付物为他人产出。
- X：检查设计全部是对已列项的逐条验证，不含任何一个专门寻找「未列出的缺口」的环节；或 critic 环节的提示词写成「确认这些项是否完整」而非「找出漏掉了什么」。
- 作废情形：工作为纯验收（已知该检什么，只需做一遍检查）；或问题空间小到「想不出漏什么」本身无价值；或输出未给出检查设计。
- 建议 k：5

**point_id: `workflow.pattern-dep-upgrade`**
- 一句话它教什么：批量依赖升级用 discover → transform → verify + **每个 bump 各自隔离的工作树**，只保留仍然绿的。
- 承重任务：要求设计一次「一口气 bump 二十个依赖」的编排。**不做这条会显形**：不知道隔离这一环时，最自然的做法是在同一工作树里逐个升，红了以后无法把绿的与红的分开保留，也无法并行编辑不冲突。
- 无压力确认：NP-A。
- X：产出的编排在同一工作树 / 同一分支上处理全部 bump；或没有 per-bump 的 gate，无法只保留通过的那些。
- 作废情形：依赖数量被减到 1–2 个（批量前提不成立）；或输出未给出编排。
- 建议 k：5

**point_id: `workflow.pattern-fan-out`**
- 一句话它教什么：综合步需要整个集合时才用 parallel barrier——「收齐」是这个模式的前提。
- 承重任务：给一个「必须拿到全部 N 份结果才能做合并判断」的任务，要求设计编排。**不做这条会显形**：不知道 barrier 前提时，会写成逐个推送给综合阶段的流式处理，或 fan-out 后不显式等待全部完成，结果不完整就先给了下游。
- 无压力确认：NP-A。
- X：产出的编排在收齐全部结果之前就把中间结果推给综合阶段，或没有任何显式的「等待全部完成」步骤。
- 作废情形：任务被改成允许增量综合（此时不需要 barrier）；或输出未给出编排。
- 建议 k：5

**point_id: `workflow.pattern-loop-budget`**
- 一句话它教什么：按共享 token budget 伸缩深度的循环，两个守卫——`budget.total` 常量检查与 RESERVE 缓冲。
- 承重任务：要求写一个「深度随预算自适应、理想轮数不可预知」的循环脚本。**不做这条会显形**：没有这两个守卫时，`remaining()` 会在缺 total 的情况下返回 Infinity，循环一路跑到 agent 上限才 cap；且最后一轮收敛没有预留额度。
- 无压力确认：NP-A —— 从零写脚本。
- X：脚本中不存在对 budget 总量的守卫检查，或不存在为最后一轮保留的 RESERVE 缓冲。
- 作废情形：轮数可前置计算（应直接用有界循环）、无 budget 约束、或单轮产出极小使 RESERVE 无意义；或输出未产出脚本。
- 建议 k：5

**point_id: `workflow.pattern-loop-count`**
- 一句话它教什么：目标 count 客观确定时用有界循环并留硬停，且要检测「连续 K 轮无新发现」以便优雅降级。
- 承重任务：要求写一个「找出 10 个 X」的循环，其中场景里客观只存在 6 个。**不做这条会显形**：不设硬停与无进展检测时，循环会为凑够 10 个一直跑下去，或死等。
- 无压力确认：NP-A。
- X：产出的循环没有轮数硬停；或有硬停但缺少「连续若干轮无新发现即停」的判定，会在只有 6 个的场景里空转到上限。
- 作废情形：目标 count 被改成不可确定（此时应用 dry-round 模式）；或输出未产出循环。
- 建议 k：5

**point_id: `workflow.pattern-loop-dry`**
- 一句话它教什么：dry-round 判停，且去重要对 **seen** 而非 confirmed——否则被拒项每轮重现、loop 不收敛。
- 承重任务：要求写一个「穷举式发现」的循环，其中会有候选被判定为不成立。**不做这条会显形**：不知道 seen / confirmed 之别时，去重会挂在 confirmed 集合上，被拒项每轮重新冒出来，循环不收敛。
- 无压力确认：NP-A。
- X：产出的循环用「已确认」集合而非「已见过」集合做去重；或用固定计数 / 主观「信心足了」作为判停条件而非 dry-round。
- 作废情形：结果集已知或足够小（此时固定计数更高效）；或输出未产出循环。
- 建议 k：5

**point_id: `workflow.pattern-multimodal-sweep`**
- 一句话它教什么：多个正交角度独立搜索 → 整体去重 → 再 deep-read。
- 承重任务：给一个「需要在大仓里找齐某类问题」的任务，要求设计搜索编排。**不做这条会显形**：不知道这个模式时，会只跑一个角度（如仅 grep 关键词）就认为发现完整，或跑完多角度但在去重前就开始 deep-read，重复读同一项。
- 无压力确认：NP-A。
- X：编排只含单一搜索角度；或多角度搜索后在合并去重之前就进入 deep-read 阶段。
- 作废情形：问题天然是单一视图或各角度重度重叠（sweep 收益有限）；或输出未给出搜索编排。
- 建议 k：5

**point_id: `workflow.pattern-pipeline`**
- 一句话它教什么：多阶段无须同步就用流式 pipeline，只有真需要整批才升级为 barrier。
- 承重任务：给一个「每个 item 可独立走完三个阶段」的任务，要求写编排代码。**不做这条会显形**：没有默认策略时，最自然的写法是先把 stage 1 结果整批收集成数组、再统一进 stage 2——命名和外观像 pipeline，实际是一个伪装成流水线的隐藏 barrier。
- 无压力确认：NP-A。
- X：产出的代码在 stage 之间做了整批收集（如把全部 stage 1 结果聚成数组后再统一进入 stage 2），没有任何 item 能提前进入下一阶段。
- 作废情形：任务被改成阶段间确需整批（此时 barrier 是对的）；或输出未产出编排代码。
- 建议 k：5

**point_id: `workflow.pattern-scout-fanout`**
- 一句话它教什么：work-list 只在运行时才能确定时，先派 scout 枚举再 fan-out。
- 承重任务：给一个「要处理的清单只有跑起来才知道」的任务，要求写编排。**不做这条会显形**：不知道这个入口形状时，会把 work-list 硬编码进脚本 / 环境变量，或用命令行参数把 scout 与处理串起来，编排对需求变化脆弱、scout 逻辑无法独立测试。
- 无压力确认：NP-A。
- X：产出的编排把 work-list 硬编码 / 从外部参数读入，而不是在编排内部由一个 scout 阶段产出后再 fan-out。
- 作废情形：work-list 被设为预先已知（此时直接 fan-out 即可）；或输出未产出编排。
- 建议 k：5

**point_id: `workflow.pattern-self-repair`**
- 一句话它教什么：单 artifact 的「产出 → 跑 gate → 把诊断喂回下一次 attempt」+ **硬 attempt cap**。
- 承重任务：要求设计一个「把一份产物驱动到通过某个 pass/fail gate」的循环。**不做这条会显形**：没有硬 cap 与诊断回喂时，产出会是无界 retry 或固定次数的裸重试；超过上限后循环继续跑，或返回未修成却不自停。
- 无压力确认：NP-A。
- X：产出的循环没有 attempt 上限；或超过上限后没有明确的停止 + 上报未修成的路径；或下一次 attempt 不携带 gate 的具体诊断。
- 作废情形：任务是多发现项去重（那是 dry-round 的职责）；或 gate 判定不严格；或输出未给出循环设计。
- 建议 k：5

**point_id: `workflow.pattern-staged-escalation`**
- 一句话它教什么：先跑便宜 pass，按信心阈值**有条件**升级到强模型，且高信心时要原样短路返回。
- 承重任务：要求设计一个成本敏感的两阶段判断编排。**不做这条会显形**：不知道这个模式时，会一上来就用强模型，或写成无条件双阶段（便宜 pass 的结果根本没被用作门控）。
- 无压力确认：NP-A。
- X：产出的编排无条件进入第二阶段；或缺少「stage 1 高信心则原样返回」的短路分支；或短路条件写反导致必然升级。
- 作废情形：便宜模型的信心度 / 错误率被设为不足以作门控（此时前提不成立）；或输出未给出编排。
- 建议 k：5

**point_id: `workflow.pattern-tournament`**
- 一句话它教什么：候选多且相对比较比绝对打分更可靠时，用两两淘汰 bracket 而不是给每个候选打 0–10 分。
- 承重任务：给 16 个候选方案，要求设计选出最优的编排。**不做这条会显形**：不知道这个模式时，会给每个候选绝对打分再排序、或设计复杂加权评分系统，浪费算力且结果不如 bracket 稳健。
- 无压力确认：NP-A。
- X：产出的编排为每个候选独立打绝对分数后排序，或让每个候选与其余全部候选都比一遍（完全图），而不是分轮淘汰的 bracket。
- 作废情形：候选数 < 4（开销不值）、绝对打分更可靠或更易解释、候选间维度不同不可两两比较；或输出未给出编排。
- 建议 k：5

**point_id: `workflow.shape-tree`**
- 一句话它教什么：按 work 形状选范式的决策树（fan-out / pipeline / loop / scout），默认用 pipeline。
- 承重任务：给一个三阶段、item 之间无共享状态的任务，要求写编排。**不做这条会显形**：语法上选对 pipeline 不难，难的是不在阶段之间偷偷共享可变状态、靠隐式执行顺序保证正确——那条未声明的顺序依赖不会被 barrier 语法暴露出来。
- 无压力确认：NP-A。
- X：产出的编排在阶段之间共享可变状态、或依赖阶段间的隐式执行顺序，而没有用 barrier 把这条依赖显式化。
- 作废情形：任务被改成阶段间确有显式依赖（此时该用 barrier）；或输出未产出编排。
- 建议 k：5

## 3. 无法预注册的 7 条（不进测试表）

方案 §7 写死了：**X 写不出来的点，不进测试。** 写不出可观测的失败形态，说明这条点自身的验收判据就没想清楚，那是另一个问题，不该靠含糊的测试蒙混过去。

下面 7 条各自说明**为什么写不出 X**，并给出该由谁去处理这个问题。三类原因互不相同，别混着读。

### 3.1 类型 A —— 只能用第 1 层测，而第 1 层不 license 删除（1 条）

**`sdd.practice-anchors`** —— 内容是五种业界 SDD 落地形态的**命名清单**（contract-first / schema-first / CDC testing / spec-kit 风格 / type-level spec）。

写不出 X 的原因：这条的全部增量是「知道这些名字与它们各自的 spec 载体」。任何要判它是否起作用的任务，落到最后都是「说得出这几种形态吗」——那是 §5.1 的**第 1 层**（直接问「这里你会怎么做」）。第 1 层能授权的只有「压成线索」，**明确不能授权删除**。而不存在这样一个承重任务：不知道这五个名字会让输出出现一个可指认的缺陷——一个 agent 完全可以在不知道「Consumer-Driven Contract Testing」这个词的情况下，做出消费者先定义合约的设计。

处理建议：这条应直接走第 1 层判「留 / 压成线索」，不进第 0 层测试表。它的母本自身也没有写「失败形态」一节——这不是疏漏，是它本来就没有。

### 3.2 类型 B —— X 与被保留的兄弟点不可分离（3 条）

这三条的共同结构：它们是**其他点的组合 / 整合**。单点消融时出现的任何可观测失败，都同时是它的组件点的失败形态，归因不成立。方案 §4 的批级消融正是为这类情况准备的。

**`devloop.taste-and-cycle`** —— 内容是把八个 dev loop 心智锚串成一张流程图 + 好 loop / 坏 loop 对照。删掉它，八个锚都还在。任何能写出来的 X（「跳过了『验收是否清楚』这一前置判断」）逐字就是 `devloop.objective` 的 X；「没读失败信号就换方向」就是 `devloop.instrument` 的 X。它自身的母本也没有「失败形态」一节。

**`workflow.pattern-pr-triage`** —— 内容是 scout-then-fanout（本批另有独立点 `workflow.pattern-scout-fanout`）+ judge-panel 的组合配方，外加一个示例脚本指针。可写的 X 要么落回 scout-fanout 的 X（对未知 list 直接硬编码），要么落到 judge-panel（不在本批的 87 条内，无法在此归因）。剩下的纯增量只有「这两个的拼接顺序」，它不产生独立可观测的失败形态。

**`workflow.pattern-test-repair`** —— 同型：fan-out test-generation（组件之一）+ per-suite self-repair-loop（本批已有独立点 `workflow.pattern-self-repair`）。X 一律落回两个组件点。

处理建议：这三条不做第 0 层单点测；把它们**直接放进批级消融的候选批**，由批级结论决定去留。批错了整批复活，这正是 tombstone 存在的理由。

### 3.3 类型 C —— 声称的增量本身是压力条件下的，本档测不到（3 条）

这三条的「失效类型」自陈：模型**已经知道**这件事，缺的是压力下不滑坡。方案 §3 写死了 `capability_gap` 问的是「无压力下它会不会做」，且承重任务一律无压力构造。对这三条来说：

- 无压力任务测出「它会做」——这与它自陈的失效描述不矛盾（它本来就说模型知道），因此**不构成删除依据**；
- 要让它显形就必须加压力（时间 / 沉没成本 / 疲劳）——而那测的是护栏档判据，**串档**。

两边都不成立，所以写不出一个既无压力又能显形的 X。

**`conduct.deserting-podium`** —— 自陈「删掉后 agent 仍抽象知道『别亲自实现』『别空等』，但失去把当下滑坡状态归类命名的能力，**压力下的漂移**不会被同一套词汇迅速捕捉」。增量明确落在「压力下的捕捉速度」这一维。

**`goal.trace-and-delta`** —— 自陈「**完全清楚**该先做 Goal Trace Test、无法追溯就先分类，但看到一件顺手又明显有价值的事时会想『先做完再解释』，是**主动绕开**分类流程而非不懂流程」。「不是不懂，是绕开」这句话本身就把它排除出了能力档。

**`devloop.explore-exploit`** —— 自陈「删掉后模型**仍知道**『该先验证方向再精修』，但一旦已经动手写出第一版方案，**沉没成本**会把它拉向『顺手做完』」。沉没成本被 §3 明确点名为要排除的压力之一；而这条的显形条件恰恰要求被测者自己先写出第一版（内生沉没成本），无法用 NP-B 的「他人产出」配方绕开——换成他人产出，被拉扯的那股力就不存在了，任务不再承重。

处理建议：**这三条的档位需要先被复核，再谈测量。** 如果它们真的是护栏档而非能力档，按 §5.2，护栏档整档「不测，留 + 加固」——那么正确的处置不是给它们凑一个测试，而是把它们的 `failure_mode` 改对。**本轮不改**（边界约束：不改任何知识图文件），只把这个不一致记在这里等审。

## 4. 三条完整推演（说明这个承重任务为什么真的承重）

「承重」的定义不是「与这条知识相关」，而是：**不做这条，输出里会出现一个可指认的缺陷；做了这条，那个缺陷不会出现。** 下面三条展开到能被审阅者复核的粒度。

### 4.1 `coordination.overlap-surface`

**母本教的是什么。** 看完同侪花名册后，逐个同侪对三样：同一批文件 / 同一个人 / 同一个产物。第三维最贵——撞上了不是重解冲突，是你做的可能整个作废。

**为什么「随便给一份花名册让它分析」不承重。** 因为文件维它会自己算。母本自己记着这个证据：一次真实编排一旦知道了同侪存在，**它自己就算出了文件重叠，没人教它**。所以一个只有文件冲突的场景，有没有这条知识，输出都一样——那个任务测不出任何东西。

**承重版本怎么构造。** 场景里必须**同时**埋三样，且让第三维成为最贵的那一条：

- 文件维：两块板都要改 `src/auth/session.ts`（**诱饵**——它会被自发抓到，用来确认任务确实被理解了）；
- 人维：两块板各有一个节点挂着等同一个人合并（队列顺序不在任何一方手里）；
- 产物维：本板节点 T-7 的输入是 `schema/user.json` 的新版本，而同侪板的节点 P-3 **正在产出**这个文件的新版本。

要求输出「重叠分析 + 本侧的顺序调整」。

**不做这条会怎样显形。** 只算文件维的输出会是这样：指出 `session.ts` 冲突、建议错开合并顺序——**看起来已经尽责，还拿出了数字**。但 T-7 会照常派出去，因为它在文件层面和任何人都不冲突。而 P-3 一旦先完成，T-7 做的东西整个作废。这个损失不表现为冲突，表现为某天发现这东西已经有人做完了——在只看输出的复核里，只能靠「T-7 有没有被挂起 / 有没有被提到」这一个可指认的点抓住它。

**为什么无压力成立。** 花名册与两块同侪板都是他人产出（NP-B），被测者没有任何已投入的工作要保护；不设期限，不说「用户在等合并」。这里唯一可能被误当成压力的是「同侪在推进」这个事实——但它是**场景事实**，不是施加给被测者的期限，去掉它场景就不成立了。审阅时若认为这仍构成压力，本条应移入 §3.3。

**X 为什么可观测。** 「输出中是否出现『依赖同一个产物』这一维、T-7 是否被挂起」——两个都是逐字可指认的，不需要评分者判断「分析得好不好」。

**作废情形为什么必要。** 如果实际跑的时候构造的花名册被简化了（比如产物维那条边没埋进去），任务就没触及适用范围，这次运行必须作废而不是记成「它没算产物维」。

### 4.2 `craft.invariant-anchor`

**母本教的是什么。** 先找到那条任何时刻都必须为真的约束，它同时决定三件事：边界划在哪、守卫放进哪个对象、拿什么测试去戳它。三个决策**绑定到同一条不变式上做**。

**为什么「让它设计一个聚合」不承重。** 因为「聚合有边界」「类要封装」「测试要测行为」这三条教科书知识它分别都有。一个只要求产出类图的任务，会得到一个边界划得很像样的答案，而这条知识的增量（三处决策**对齐到同一条约束**）根本没有机会显形。

**承重版本怎么构造。** 任务必须**同时索要三样产物**，并且领域里要有一条明确的、非平凡的不变式：

> 设计一个「团队席位配额」模型：一个团队有 `seat_limit`，成员加入时不得超过它。请给出 (1) 聚合边界与类结构，(2) 加入成员这一操作的方法实现，(3) 你会写哪些测试。

不变式是「成员数 ≤ seat_limit，任何时刻」。这条约束**同时**回答三问：边界必须把 team 和 members 圈在一起（否则无法原子检查）、守卫必须住在 team 的加入方法里（不是外部 validator）、测试必须戳「直接操作实体会不会被挡下来」。

**不做这条会怎样显形。** 最自然、最像样的错误答案是母本点名的那个：把校验逻辑放进一个 `SeatLimitValidator` service，team 类保留公开的 `addMember`，测试只测那个 validator 本身。**表面上有一个聚合类、也有测试，看起来合规**——三样都产出了，每一样单看都不错，只是三处决策各自独立做出、互不对齐。任何调用方绕过 validator 直接改状态都不会被挡，而这件事从没被测过。

**为什么无压力成立。** NP-A：从零设计，不给半成品（没有既有 validator 可以复用，因而没有沉没成本），不设期限，一次输出即可判。

**X 为什么可观测。** 两个逐字可查的点：(a) 守卫是否在实体的方法内部并真正拒绝，还是在一个外部可绕过的 validator 里；(b) 测试列表中是否存在一条「绕过正常入口直接改状态会被挡下」的用例。都不需要评分者判断代码好不好看。

**作废情形。** 若产出未具体到方法体 / 测试列表级别（只给了类名与目录），输出不可判，作废。

### 4.3 `scheduling.node-contract`

**母本教的是什么。** 派发前定五要素：Input deps（pin 住上游产物 version/hash）、Output schema、Success predicate（**优先给可执行的验收物**——一个会失败的测试、一份评分标准、一个真实样例或反例，而不是散文式描述）、Timeout + budget、Escalation condition（何时 STOP 并返回 escalation 结果）。

**为什么「让它写一份派发指令」不承重。** 因为「派发要写清楚」是通用常识，任何模型都会写出一份看起来完整的指令。更麻烦的是：**五个字段填满这件事本身，正是这条知识的隐蔽失败形态**——母本明确写着，字段可以表面填满、通过「有没有写全」的形式检查，而 escalation condition 写成「遇到困难及时上报」这类没有可判定阈值的套话。所以一个只检查「五项齐不齐」的任务，会把最典型的失败判成通过。

**承重版本怎么构造。** 任务必须让**套话型 predicate 与套话型 escalation 在这个具体场景里是不够用的**，也就是场景本身要有一个明确的失败模式在等着：

> 派发一个节点：把仓库里 14 个模块的错误处理统一到新的 `AppError` 体系。已知其中 3 个模块的现有错误语义与新体系不完全对得上，具体是哪 3 个事先不知道。请写出这个节点的派发契约。

这个场景里，「遇到困难及时上报」永不会触发——执行者会在那 3 个对不上的模块上反复重试到耗尽预算，因为它自己也不知道自己撞上的是「该上报的语义冲突」还是「一个还没想明白的实现细节」。同样，「统一好错误处理」这种散文式 success predicate 会被执行者和派发者各自脑补成两个东西，分歧要到交付才暴露。

**不做这条会怎样显形。** 输出是一份五项俱全、读起来很专业的派发指令，其中：success predicate 写成「所有模块使用统一的 AppError 体系，代码风格一致」（散文，无可执行验收物），escalation condition 写成「遇到阻塞或不确定时及时反馈」（无阈值，永不触发）。形式检查全过。

**为什么无压力成立。** NP-A：从零写契约，不给已有的指令草稿（避免「改别人的比重写省事」），不设期限，一次输出即可判。这条特别需要注意的是**不能**在任务里提示「注意五个字段」——那会把第 0 层（自发做出）降级成第 1 层（照单填表）。

**X 为什么可观测。** 两个可逐字引用的点：(a) success predicate 是否给出了可执行的验收物（一条会失败的测试 / 一份评分标准 / 一个具体样例或反例），还是只有散文描述；(b) escalation condition 是否含可判定的阈值（如「同一模块连续两次尝试未通过 gate」「发现语义冲突时立即返回冲突清单」），还是「遇到困难及时上报」这类永不触发的套话。评分者不需要判断契约写得好不好，只需要判断这两处是不是可判定的。

**作废情形。** 若输出未产出派发指令，或场景被改成节点小到不跨执行边界（orchestrator 自己执行的原子协调动作不需要五项契约），作废。
