## 结论一（已完成·确定性）：59 条对 ccm 命令面的断言，**零漂移**

方法：抽出每条母本正文里的每个 `ccm <verb>` 与 `--flag`，与真实 CLI 的 `--help` 语料（219 个命令前缀、203 份有效 help、100KB）逐 token 比对。

初跑 23 条有 miss，逐条追查后**全部归因，无一条是真漂移**：

| miss 类别 | 例 | 判定 |
|---|---|---|
| 属别的命令面 | `--force-takeover` / `--resume`（`as-master-orchestrator` 的 flag） | 不是 ccm 的，正确缺席 |
| 属别的 harness | `--sandbox` / `--yolo` / `--last`（codex / cursor-agent 的 flag，被当 provider 事实引用） | 正确缺席 |
| 我的正则伪影 | `--graph--biz`（从 `--graph`/`--biz` 粘连）、`--legacy-wakeup`（从散文 "legacy `wakeup`" 粘出） | 装置缺陷，非知识缺陷 |
| 我的取样缺陷 | `--review-verdict` 在 `ccm task done --help` 里，初版只抓了命名空间层 | 装置缺陷，已修 |

**这是 `ccm` ⟷ `using-ccm` 锁步纪律仍在生效的机械证据**——不是靠人自觉，是逐 token 对得上。

> **但这个结论不 license 任何删除。** 它回答的是「这条点提到的命令是否真实存在」（必要条件），不是「`--help` 是否教了同一件事」（充分条件）。把前者当后者用，正是方案 §3 列的任务效度威胁。

## 结论二（方法修正）：D 层的 oracle 有**两种形态**，方案里只写了一种

方案 §5.1 把 D 层写成「与 `--help` 比对」。跑到转录密度最高的 `point:ccm.footgun-table`（0.96）时发现写窄了：

**那条点根本不是 `--help` 的转录，是「症状 → 诊断」表。** 它每一行的左列是一个可观测的报错，右列是成因与修法。对它而言：

```
--help          回答「有哪些 flag」        ← 对这条点几乎无关
真实错误 / lint  回答「刚才为什么被拒、怎么修」 ← 这才是它的 oracle
```

**修正**：D 层 oracle = `--help` ∪ **真实错误消息 / lint 输出**。后者需在隔离 home 里真实触发，成本仍然极低，且结论同样确定。

## 结论三（方法修正）：表格型点的处置单元是**行**，不是点

实测 `ccm.footgun-table` 的 5 行，得到 3 种不同判定：

| footgun 行 | 实测触发结果 | 判定 |
|---|---|---|
| `task update --set status=done` 被拒 | `rc=3` · `refused: "status" is a load-bearing (🔒) task field; use the dedicated command (task set-status / task add-dep / task update --parent)` | **接口已代劳** —— 连 🔒 符号与补救 verb 都说了 |
| `board update --goal` 在新板被拒 | `rc=3` · `refused: active Goal Contract cannot be bypassed by board update --goal; use \`ccm goal amend\`.` | **接口已代劳** —— 修法逐字给出 |
| `block --on user` 缺 decision_package | `rc=3` · lint 给出规则 + **为什么**（「没包 = 新 session 开不起讨论，采访闭环塌掉」）+ 怎么修 | **接口已代劳，且比母本讲得更全** |
| `task done` 从 `ready` 直接跳 | `rc=3` · `illegal transition: ready → done. legal next from "ready": in_flight, blocked` | **部分** —— 告诉你合法后继状态，没告诉你产生 `in_flight` 的 verb 叫 `task start` |
| `task show <不存在 id>` | `rc=0` · `{"ok":true,"data":null}` —— **不报错、不提示** | **未代劳** —— 接口无法警告自己的沉默 |

最后一行是这一层最有价值的一类：**接口能陈述它做了什么，无法陈述它「什么都没做」。** 凡是「静默成功 / 空结果 / 无信号」形态的知识，oracle 恒定为「未代劳」，必留。

由此得出一条处置规则：

> **表格型的点，判定落在行上。** 整条判「删」或「留」都会错——它是若干条独立事实的容器，不是一个命题。

被这条规则影响的点（正文以表格为主体）：`ccm.footgun-table` / `ccm.board.validation-rules` / `ccm.cmd.*` 一族 / `ccm.board.task-fields` 等，占 59 条中的多数。**这会显著抬高 D 层的实际工作量**——原估「59 条比对」实为「59 条 × 平均十余行」。

## 结论四：exit code 断言核准

母本多处断言 `exit 3`。实测（正确捕获退出码，非管道尾命令的退出码）：

```
task update --set status=done   rc=3  ✓
task done (ready→done)          rc=3  ✓
task block --on user 缺包        rc=3  ✓
board update --goal (新板)       rc=3  ✓
task show <不存在>               rc=0  ✓（母本正确记载了「不报错」）
```

**全部与母本一致。**

> 自己踩的坑记一笔：首轮用 `cmd 2>&1 | head -c 500; echo rc=$?` 取退出码，拿到的是 `head` 的退出码（恒 0），差点据此写下「母本断言 exit 3 但实测 rc=0」的假漂移。**管道会吞掉被测命令的退出码**——测 exit code 必须直接捕获，不能经管道。

## 结论五：命令目录一族的判定 —— 可切成两半，一半删一半留

拿两条做了完整并排（`ccm.cmd.calibration` 全文、`ccm.cmd.jc` flag 表），结果一致且干脆：

### 覆盖的那一半（help 逐字，且更全）

`ccm calibration capture` 的对照：语法行、`positional：无`、6 个 flag 的类型与含义、两条示例——**全部逐字对得上**，连示例参数 `--scope this-board --as-of 2026-07-20T12:00:00Z --json` 都一模一样。且 help 的措辞更精确（`--effective-n`：help 说「号池有效配额份数覆写」，母本只说「只缩 throughput 参考」）。

`ccm jc add` 的 flag 表：`自决类别` / `严重度` / `做了什么决定` / `为什么这么决` / `影响面 / 反转代价` / `佐证引用` / `关联 task` —— **七条描述与 help 字节相同**。

> **⚠ 已撤回的一处论断**：此处原写「母本表遗漏 `--set` / `--set-json`，是有损副本」。**该论断为假**——当时只看了 `head -12` 的截断输出，表在第 12 行之后仍在继续。精确集合比对：母本 flag 集 `{category, decision, impact, json, note, rationale, refs, set, set-json, severity, status, task-ref}` 是 help 集 `{category, decision, impact, rationale, refs, set, set-json, severity, task-ref}` 的**超集**，一个都没漏。
>
> **重复本身仍然成立**（七条描述与 help 字节相同），「有损」这一层不成立。
>
> **⚠ 后续追加**：原文这里写「主论据的实证支撑改由 §6.1 的 `FMT-POLICY` 漂移承担」——§6.1 那条**随后也被证伪**（见该节）。故本轮**没有任何一条实测支持「副本会骗人」**；恰恰相反，两次找漂移都以「无漂移」告终。迁移的理由只剩**结构性**的那条（副本天然可能过期、且要人维护），不再有本仓的实例支撑。

### 未覆盖的那一半（help 不说，必留）

同一条 `calibration capture` 里 help 完全没说的：

- **「只读 board」** —— 这个命令不改窄腰字段。
- **`board_id` 是 canonical board 路径的 SHA-256** —— 为什么不用可变的 goal / session 当实体键。
- **`snapshot_id` 的构成、无 deadline 时跳过落盘** —— 幂等的具体语义。
- **边界**：只采预测侧；label 回填与 calibration flip 不在此命令内；`estimate deadline-risk` 纯只读、绝不创建 store。

一句话：**`--help` 回答「怎么调」，母本这一半回答「它对世界做了什么、什么它不做」。后者没有任何接口会说。**

### 由此得出该族的处置规则

> **命令目录点 = 语法 / flag 表 / 示例（删，接口逐字覆盖且更全）+ 语义段（留：行为、身份、幂等、边界、footgun）**

### 这对锁步纪律的影响（要点，需用户拍板）

项目纪律要求 `using-ccm` 与 `ccm` 命令面**逐条锁步**，理由是让 agent「一次写对不撞 exit 3」。实测证据指向一个反直觉的结论：

**被删掉的恰好是锁步负担的全部来源。** 语义段不随 flag 增删而过期，flag 表才是；而 flag 表正是接口自己能免费、准确、实时提供的那部分。删掉它：

- 锁步义务大幅缩小（语义段的漂移面远小于 flag 面）；
- **正确性上升**——`--help` 不会过期，副本会（本次已抓到 `jc add` 缺两个 flag 的实例）；
- 代价是 agent 多一次 `--help` 往返。

这是一次 token 与往返之间的交换，**不是能力交换**。但它触及一条成文纪律，属用户拍板范围，此处只出证据不做决定。

## 量化（口径已修正）

初版给过一个「19% 疑似逐字重复」，**那个数不能用**——度量把「看起来像命令语法」当成了「被 help 覆盖」，于是把 `ccm.hotpath-flows` 这类**带意图注释的动作序列**（「起步：建板 → 转写 Goal Contract → 确认 DDL → 完整性检查」）也算了进去。任何单条 `--help` 都不含这种流程。

修正后的口径：

| 成分 | 字符 | 占 59 条 | 判定 |
|---|---:|---:|---|
| flag 表行 | 23,132 | **9%** | help 逐条覆盖 → **可删** |
| 「例：」行 | 8,294 | 3% | help EXAMPLES 多数覆盖 → 抽验后删 |
| 代码围栏 | 38,083 | 15% | **含流程序列，须逐条人判**，不可一概而论 |
| 其余（语义散文） | 190,319 | 73% | 默认留 |

**这次修正的教训与前一次同源**：机械度量测的永远是它能测的东西（形状），不是你想要的东西（语义覆盖）。拿形状代理语义，会在最像的地方错得最狠——`hotpath-flows` 的形状与 flag 表几乎一样，语义性质完全相反。

## 结论六：`ccm.board.validation-rules`（17KB，最大留守项）—— 判定按规则一分为二

### 6.1 集合对账：**零漂移**（初判有误，已撤回）

| 来源 | 条数 |
|---|---:|
| 引擎 `board-model.ts` registry | 84 |
| 母本 `validation-rules` 源码 | 83 |

初判：差集精确到一条 `FMT-POLICY`，母本零命中 → 报为「唯一一条真漂移」，并写进本文、口头向用户重复。

**该判定为假。** `FMT-POLICY` 在母本里合法地写成投影占位符 `{{USING_CCM_FMT_POLICY_ROW}}`（由三个 host 的 `adapters/*/strategy.yaml` 定义），投影后**已分发产物 `plugin/dist/claude-code/skills/using-ccm/references/board-model-guide.md` 里有这一行**，内容与引擎一致。

**错在比对层错位**：拿**母本源码**对**引擎**，而 SAP 架构下母本源码不等于分发内容——中间隔着 adapter 投影。正确的比对对象是投影产物。

> 修正后的结论：**规则集零漂移，`ccm` ⟷ `using-ccm` 锁步纪律完好。** 这个结论比原先那条更强，也更值得记——它说明这条靠人自觉的纪律，在 84 条规则上一条没漏。

### 6.2 实质比对：四条取样给出的印象是错的

先取了 `FMT-DEPS` / `BIZ-DONE-VERIFIED` / `GRAPH-CYCLE` / `BIZ-TIME-ORDER` 四条并排，结论看起来很干脆——引擎消息**严格强于**母本行：

```
母本行:  | FMT-DEPS | hard | deps 缺失、非数组… | deps 是钉死窄腰字段，必填；无上游写 --deps
引擎消息: "T1.deps 缺失。deps 是钉死的窄腰字段（与 id/status 同级），不是可省略的柔性边。
          坏什么：缺 deps = 畸形窄腰；下游图校验把它当无上游，让「手编 tasks[] 忘写 deps」
                  这个真实错误静默溜过。
          怎么修：补上 deps——无上游写 "deps": []，有上游写 "deps": ["<上游 task id>", …]。"
```

引擎多出**「坏什么」**（为什么要紧），且修法带实际 id。照这四条，`validation-rules` 该整条删。

**然后统计全量，结论翻转：**

| 76 个被 emit 的规则码 | 数量 |
|---|---:|
| 每处 emit 都带「怎么修」 | **20** |
| 部分带 | 1 |
| **一处都不带** | **55** |

**我那四条全部落在最好的 20 条里。** 四取样的选择本身不是随机的——我挑的是「看起来典型」的，而典型在这里恰恰等于「写得好」。

### 6.3 由此得出的判定（按规则分两半）

| 规则组 | 数量 | 判定 |
|---|---:|---|
| 消息已含「坏什么 + 怎么修」 | 20 | **删母本行** —— 有损副本，引擎消息更全 |
| 消息只报「什么不对」，无修法 | 55 | **必留** —— 母本的「怎么修」是**该修法在全仓的唯一陈述处** |

**删这 55 行 = 把修法从系统里抹掉。** 它们不是重复，是唯一副本。

### 6.4 派生的 ccm 侧工作项（不在本轮）

上面这个二分给出一条比「删/留」更好的路：**把那 55 条的修法迁进 emit 消息**，参照已有 20 条的写法（`什么不对 + 坏什么 + 怎么修`）。迁完之后它们自动落进「可删」那一半。

这与「完善 ccm 各命令 help」是同一件事的另一半——**help 管「调用前怎么写对」，lint 消息管「写错后怎么改对」**，两者都是接口自我说明能力，都该由 ccm 承载。

**顺序仍是先补后删**，且这次尤其硬：这 55 条修法目前没有第二个副本。

### 6.5 母本剩下该留的部分

即便 20 条行删掉、55 条日后也迁走，`validation-rules` 仍有不可迁的内容：

- **规则族的构成**（FMT 形状 / GRAPH 图 / BIZ 业务三族各管什么）——跨全部规则的分类心智。
- **hard 与 warn 的分野**（hard 阻断写入、warn 只提示）——跨全部规则的严重度语义。
- **规则总数与「全集」承诺**——让 agent 知道这套约束是封闭的、可穷举的。

这三样任何单条 lint 消息都说不了，属跨规则知识 → 留 skill。**与命令目录那族的切法同型**：逐条事实归接口，构成与心智归技术文档。
