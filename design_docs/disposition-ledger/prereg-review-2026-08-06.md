## 总判：**有条件能跑**

这份表的**逐条工艺水平明显高于我预期**——X 绝大多数是可逐字指认的结构或缺失，作废情形写得真、不是摆设，§4 三条推演能被复核，§6 主动自曝了 22 条档位张力而没有粉饰。它不是一份需要推倒重做的表。

但它**现在不能直接拿去跑**，卡在一处结构性的、而非逐条的问题上：

> **表里写的是「承重任务」的一句话设计意图，不是真正要投喂的提示词。而 §11 试点证明，泄题恰恰只发生在提示词那一层。**
>
> 后果不是「可能测不准」，而是**判据静默串档**：一道泄题的承重任务把第 0 层（自发做出）降级成第 1 层（点了题再展开），而 §5.1 写死第 1 层**只授权压成线索、绝不授权删除**。降级是静默的——记录格式里没有任何字段会留下「这一条其实是第 1 层结果」的痕迹。跑完之后，一批实为第 1 层的通过记录会以「第 0 层 k 次全中」的名义进入候选删除批。

我按试点的办法实测了一次（详见 Q2）：**6 道承重任务里，4 道被未读原文的第三方高把握地反推出考点，1 道方向正确，1 道没泄。** 泄题率与试点的 7/7 同一量级。

所以条件是：**补上一层「跑之前的泄题闸 + 跑之后的降级记录」，再修掉下面点名的几条不承重项，就可以跑。** 这些条件是可执行的，不需要重做整张表。

## Q1 承重任务真的承重吗

抽查 **15 条，覆盖 12 个 skill**（capacity / control / coordination / craft / ddd / devloop / oop / routing / scheduling / slicing / verification / workflow）。结论分四类。

### A. 真承重（5 条，是这份表的质量上限）

**`coordination.overlap-surface`（§4.1）** —— 全表最好的一条。它做了别处都没做的一件事：**埋诱饵**。文件维（`src/auth/session.ts`）明知会被自发抓到，专门用来确认任务被理解了；真正的判据落在产物维（T-7 的输入 = 同侪 P-3 正在产出的 `schema/user.json`）。这使「输出很尽责但漏了那一维」和「根本没理解任务」可以分开。而且它引用了母本自陈的反证据（一次真实编排自发算出了文件重叠），**主动论证了朴素版任务为什么不承重**。这是承重论证该有的样子。

**`craft.invariant-anchor`（§4.2）** —— 承重来自「**同时索要三样产物**」（边界 + 方法实现 + 测试列表）。单要类图会得到一个像样的答案而增量（三处决策对齐到同一条约束）没机会显形；三样一起要，`SeatLimitValidator` 那个反例就必然暴露。构造与增量严格对应。

**`scheduling.node-contract`（§4.3）** —— 承重来自「3 个对不上的模块，**具体是哪 3 个事先不知道**」。这一句让「遇到困难及时上报」这类套话 escalation 在这个场景里**可证明地永不触发**，从而把「五项填满」与「五项可判定」分开。这正是母本点名的隐蔽失败形态。

**`craft.composition-over-wrapper`** —— 任务是一件普通设计活（给已有 repository 接口接入外部支付服务），不预先给分类框，缺陷（只转发的 `PaymentManager`）在产物里可方法级指认。**它也是 6 道盲测里唯一没泄的一道**（见 Q2），这不是巧合，见 Q2 末尾的形状规律。

**`ddd.aggregate-ownership`** —— 承重来自「要求写出下单用例的**持久化步骤**」。类图边界很容易划对，只有落到事务这一层，运行时边界悄悄合并才会现形。构造精确命中了母本说的那个「只有写出持久化步骤才暴露」。

### B. 不承重 —— 必须改（3 条）

**`control.decision-program`（原文：「给一块 WIP 上限为 3、当前在飞 1、ready 集合里有 4 个互不依赖任务的板，要求写出本回合收尾要做的全部动作」）**

X 要求「只派出 1 个即宣告收尾」。但**把在飞补到 WIP 上限是纯算术**，不需要任何「循环回顶部」的结构。盲测第三方看到题干的第一反应就是：「从 4 个 ready 里再派 2 个（1+2=3）」——**它没有这条知识，却给出了 X 判为通过的答案。** 这道题几乎必然产出「自发做到」，而那个通过与母本主张（回合内循环、直到 ready 真空）无关。

X 的第二个合取项「没有任何一句表示派完后回到顶部重判」也救不了：它只考措辞，而且是**合取**，第一项不成立整个 X 就不成立。

要承重，场景必须让**线性检查表可证明地漏掉东西**——例如派发某个节点会当场解锁一个新的 ready 任务，或存在需过 fill-work 准入的活；只有回到顶部重判才会看见它。现在的场景做不到这件事。

**`slicing.example-contrast`** —— 母本自陈「只是一个用来校准直觉的对照样例，**不单独定义判断标准**」，且「换一个论域，例子里的具体结论未必还成立」。表里给它构造的任务（没有共享底座的目标，看会不会硬造一个最薄前置片）测的是**兄弟点 `slicing.walking-skeleton` 被误用**，不是这一条自身的增量；而 `walking-skeleton` 已在 §0.5 改档移出。X 描述的失败（无端造一个不产出端到端价值的前置片）**基线发生率极低**，k=5 全过是默认结果、零信息量。

表自己标了「档位疑议」并限定不得据以单条判删——但那个处置不够：它不该留在第 0 层。它的结构与 §3.2 类型 B（X 与被保留的兄弟点不可分离）**完全同型**，应当移进 §3.2 走批级消融。

**`scheduling.dag-and-critical-path`** —— 两个独立缺陷。① X 带逃生舱：「没有调用任何图分析工具，**也没有**写出可复核的逐节点推导」——任何认真的模型都会把推导写出来，于是必然通过，而母本主张的恰恰是「该交给机器算」，不是「写清楚就行」。② 母本明写「**两侧都是错**」（复杂图心算 / 平凡图仪式性跑工具），任务只构造了一侧；作废情形提到了另一侧却没有对应任务。一个单侧通过被记成「自发做到」会**超额宣称**。

### C. 承重成立，但档位与判据串档 —— 会朝「过度删除」方向出错（3 条实例）

这三条的母本 `失效类型` 标着「主体：事实方法」，**但正文是纯动机措辞**：

- `routing.qualification-and-fallback`：「**知道**容量证据必须和目标绑定在同一个来源…**但容量紧张时会倾向于**把相近但不严格对应的证据当成够用」
- `oop.abstraction-cost`：「**知道**『配得上开销』的判断标准，**但**面对一个能预见到的未来需求，**会倾向于**提前把接缝建好」
- `devloop.ledger-when`：「**知道**哪些信号该触发写 ledger，**但在『先把活干起来』的冲动下会**把这件事往后拖」

对这三条，无压力任务测出「它会做」与母本自陈**完全不矛盾**（母本就说它知道）。但第 0 层的通过会把它送进候选删除批——这正是 §3 构念效度那条威胁的实现形态，**且方向是删除许可这一侧**（§6 说误删的代价是静默能力回归）。

规模：我机械扫了存活的 73 条母本 `失效类型`，命中动机措辞的有 **17 条**——与 §6.3 自述的「其余 17 条照常留在表内」逐字吻合，作者的清点是准的。但这 17 条**不是同质的**：

- 有 2 条母本已显式自标「双重性质·方法部分补不回来，它才是承重结构」（`scheduling.node-contract`、`outside.falsification-and-calibration`）——这个切分我认可，它们可以留；
- 有的（如 `workflow.shape-tree`：「概念上知道并行和流水线的区别，**但不知道这个 workflow 系统具体提供哪几种原语**」）其实是真知识缺口，我的正则误命中，可以留；
- 上面点名的 3 条既无双重性质声明、正文又是纯动机，**留在第 0 层没有依据**。

§0.5 的档位重判已经移走了 9 条，但**没有触碰这 17 条**。作者在 §6.3 说「这个 22 : 3 : 2 : 17 的划分是我的判断，需要独立复核」——**这就是那次复核，结论是 17 里至少 3 条要再动。**

### D. 承重成立但受基线发生率拖累（1 条）

`craft.shared-spine` —— X 是「三份产物中同一术语的定义**存在**可逐字指认的冲突，且自查段落声称一致」。它要求被测者**自发产出一个自相矛盾**才算失败。这件事的发生带随机性，k=3 不足以把「它有统摄框架」和「这三次碰巧没矛盾」分开。判「不冲突」还需要评分者做语义比对，而不是指认结构。它不该被当成 k 次全中的存在性证据源。

### Q1 小结

抽查 15 条：**5 条真承重、3 条不承重必须改、3 条档位串档、1 条基线发生率过低、3 条（`capacity.task-first-allocation` / `ddd.design-focus` / `devloop.objective`）承重成立但泄题（见 Q2）。** 按这个比例外推，73 条里估计 8–12 条需要重做或移档。这不是「表写坏了」，是可逐条修的量。

## Q2 承重任务会不会把答案递到手上 —— **会，这是本次审查最重的一条**

### 做法

我先声明一个方法论限制：**我自己已经通读全表，无法对自己做干净的盲测。** 所以我按试点 §11 的办法，把 6 条承重任务的**题干部分**（剥掉 point_id、剥掉「一句话它教什么」、剥掉「不做这条会显形」这段明显泄露的作者旁白）单独交给一个**未读本仓任何文件、被禁止检索**的第三方，只问两件事：「这个任务显然期望执行者做什么？」+「把握程度」。

### 结果：6 道里 4 道高把握命中，1 道方向正确，1 道没泄

| 条目 | 第三方只看题干说出的 | 把握 | 判定 |
|---|---|---|---|
| `craft.composition-over-wrapper` | 给了两个互斥候选（适配层隔离 / 别加空转 wrapper），自述基本属泛泛而谈 | 低 | **未泄** |
| `ddd.design-focus` | 「幂等是消息契约必须现在定；重试间隔只是可调旋钮推迟。考的是识别这两项被故意混在一起、不能按『都是可靠性配置』一并推迟」 | 高 | **泄** |
| `scheduling.node-contract` | 「契约里必须为未知的 3 个不对齐模块预留出口：遇到语义对不上要停下上报而不是自行硬凑；同时给出可判定的完成边界」 | 高 | **泄** |
| `verification.heterogeneous-review` | 「不采信生产者自报，由独立第二方对着验收标准复核并留证据」 | 中 | 半泄（方向对，未及「换族不换壳 / 不带 framing」） |
| `control.decision-program` | 「从 4 个 ready 里再派 2 个（1+2=3），回合结束前不留可派发的空位」 | 高 | **泄**（且顺带证明了 Q1-B 的不承重判定） |
| `devloop.regularize` | 「选直接方案。为『将来可能』引入的插件机制是未兑现的复杂度（YAGNI / 简单性即正则）」 | 高 | **泄** |

第三方自己的收尾判断：「6 道里我认为有 4 道是猜到了具体考点而不是泛泛给建议。」

### 这意味着什么

试点 §11.3 的结论**在第 0 层同样成立**：

> 一个足够具体到能判分的场景，必然具体到能反推答案。

第 0 层原本比考试形态多一层保护——它索要的是一件**真实工作产物**，缺陷在产物里显形，而不是让被测者回答一个问题。**这层保护在一部分条目上是真的，在另一部分上是假的。** 分界线看得很清楚：

- **未泄的形状**：要求交出一件普通工作产物，判据是「产物里有没有那个缺陷」。`craft.composition-over-wrapper` 说「设计接入一个外部支付服务的代码结构」——这句话对任何设计任务都成立，考点藏在产出里。
- **泄了的形状**：题干**先把被考的那根轴摆出来**，再要求沿这根轴做判断/分类/排序/选择。`ddd.design-focus` 说「分成『现在定』与『推迟到实现』两栏」——这个二分**就是**这条知识本身；被测者拿到的不是「你会不会想到该分」，而是「给你这个分法，你会不会分对」。那是第 1 层。

**这个形状差别是可机械筛的。** 我扫了全表 80 条的题干动词，明确要求「评审 / 评估 / 判断 / 判定 / 分成 / 排序 / 选一个 / 逐片检查 / 各判 / 诊断」的有 **22 条**（其中 3 条已改档移出，**存活 19 条**）：

```
craft.layered-thinking · ddd.design-focus · ddd.failure-radar · devloop.regularize
distill.routing-tree · distill.taxonomy · oop.failure-radar · oop.four-pillars
oop.solid-judgment · outside.evidence-levels · routing.qualification-and-fallback
scheduling.parallelism-and-granularity · sdd.admission · sdd.core-belief
slicing.antipatterns · slicing.grain · slicing.value-risk
verification.hash-and-stale · workflow.admission
```

这 19 条是**高泄题嫌疑名单**。注意它不等于「必然泄」——`sdd.core-belief`（给一段测试写于实现之后的代码，问验收有效性）泄的程度就比 `ddd.design-focus` 低，因为它没有把「先于实现的外部标准」这根轴摆出来。所以这份名单是**优先审查队列，不是自动作废清单**。

### 关键后果：降级是静默的

第 0 层与第 1 层的授权差是**质的**（进候选删除批 vs 只能压成线索、绝不删）。而一道泄题的承重任务把前者变成后者，**记录里不会留下任何痕迹**——预注册模板没有这个字段，§5.3 的跑测纪律只写了「不得出现被测知识的关键词或字段名」，而试点已经证明**关键词回避是不够的**：泄的不是词，是场景结构。

这是我判「有条件能跑」而不是「能跑」的**唯一硬理由**。

### 还有一处：真正要投喂的提示词不存在，所以审不到

表里每条只有一句话的任务设计意图（「给四个任务（长而机械 / 短而不可逆 / 长而高风险 / 短而机械），要求各配一个模型档」）。真正决定泄不泄的是**那四个任务被怎么写出来**——如果标签逐字照抄进提示词，「机械 / 不可逆 / 高风险」就是风险轴本身，泄得比 `ddd.design-focus` 还彻底；如果写成四个具体的活让被测者自己看出来，就不泄。

**这份表现在无法被审出这个差别，因为那段文字还不存在。** 而按目前安排，它会由跑测的人现场写——那正好把 §3 那条「作者 / 任务设计者 / 评分者同一人」的冲突从设计环节挪到执行环节，而不是消除它。预注册的全部价值在于「跑之前写死」，**提示词没写死，就等于没预注册。**

## Q3 「若这条不起作用，输出应出现 X」写得可判吗

**整体是合格的，且明显好于 §1.3 立的最低标准。** 我通读了全部 80 条 X，没有一条落进 §1.3 点名的「输出会变差 / 质量下降」这类禁区；绝大多数是可逐字指认的结构或缺失（「产出的循环没有 attempt 上限」「矩阵中出现至少一个不在给定清单里的事件名」「守卫只以注释形式存在」）。

写得最差的三条：

**① `oop.abstraction-cost`（最差）**
> X：…或用「删掉这层少了什么」自问自答，而答案里指认的接缝**正是为服务这层新抽象才创造出来的（循环论证）**。

「判定一段推理是不是循环论证」是**判断，不是指认**。§1.3 要求 X 是「一个存在的结构、一个缺失的字段、一个可以逐字引用的句子」，这一项三样都不是。两个评分者对同一段自问自答给出相反判定完全可能，而这里没有任何可对照的锚点。第一个合取项（「决定现在抽出接口，理由只指向尚未确认的未来变体」）是可判的——**第二项应当直接删掉**，留着只会制造分歧。

**② `scheduling.dag-and-critical-path`**
> X：输出给出具体的临界链与时间数字，但过程中没有调用任何图分析工具，**也没有写出可复核的逐节点推导**。

两处问题。逃生舱：「写出推导」这一条任何认真模型都做得到，于是 X 事实上不可能成立——一个**永不触发的 X 等于没有 X**（这恰恰是 §4.3 自己批评 escalation 套话时用的同一个论证）。工具依赖：「有没有调用图分析工具」取决于跑测环境给不给工具，而隔离要求（试点 §5）是在空目录里跑不带插件——那样这一项恒为真，X 又变成恒成立。**同一条 X 在两种环境下分别恒假与恒真，说明它测的不是被测者。**

**③ `craft.shared-spine`**
> X：三份产物中同一术语 / 契约的定义**存在可逐字指认的冲突**（如设计说明称支付成功即已支付、测试断言要求回调确认后才算），且自查段落声称三者一致。

「可逐字指认」这个限定是真诚的努力，但它要求 X **由被测者自发制造**。若这一轮它碰巧没矛盾，记的是「自发做到」；k=3（本条已降 k）不足以把能力和运气分开。另外「同一术语的定义是否冲突」在边缘情形仍是语义判断——括号里给的例子很好，但那只覆盖了一种冲突形态。

**另外两个跨条目的通病，比上面三条影响面更大：**

**布尔结构无括号，或/且混用处歧义。** 例如 `workflow.admission`：「给小场景判定上 workflow，**或**给大场景判定继续用零散 subagent；**且**判断依据中不出现规模 / context 隔离这两条门槛中的任一条。」`且` 是同时约束前面两个分支，还是只约束后一个？两种读法给出不同判定（判断正确但理由里没提门槛：一种读法算通过，另一种算 X 成立）。`craft.layered-thinking`、`oop.failure-radar` 同型。双评分歧会集中在这里，且**是判据的锅不是评委的锅**。建议跑之前把这类 X 改写成显式编号的判定步骤。

**「不含任何一句 X」这个句式占比偏高（24 条）。** 它把「做没做到」替换成「说没说到」。多数条目里它是第二合取项、前面有实质行为判据兜底，所以可接受；但 `distill.routing-tree` 的 X 几乎完全落在措辞上（「归宿依据中不出现『换个项目还有用吗 / 这是机制还是判断 / 需不需要专职角色视角』这三问中的任一问」）——一个用不同词把三条经验都路由对了的答案，判起来会很尴尬。这一条建议改成判**路由结果**而非判用词。

## Q4 无压力确认是否真的成立

**大体成立，且做得比我预期认真。** NP-A/B/C 三个配方是这份表的一处真设计，不是形式主义：多条在配方后面附了具体的消除理由（`sdd.core-belief`「关键：消除返工代价摆在眼前的沉没成本」、`multilayer.admission-and-escalation`「**不告知已投入多少**」、`devloop.plateau-restart`「被测者对已投入的五轮不负责」）。§4.1 甚至主动讨论了「同侪在推进」这个场景事实算不算压力，并写下「审阅时若认为这仍构成压力，本条应移入 §3.3」——这是负责任的写法。

80 条全部填了「无压力确认」字段，无遗漏。三个配方之外没有夹带期限措辞、既往投入提示或催促。

**混进来的压力：我判有 1 条明确、2 条边界。**

**明确一条 —— `verification.heterogeneous-review`**
> 承重任务：给一个**临界路径上** correctness-critical 的 `done` 候选…
> 无压力确认：NP-A —— 从零设计验收安排；不设期限。

「临界路径」不是中性事实，它的定义就是「这里每拖一天，全局拖一天」。它在场景里的作用与「时间不多了」等价，而且方向明确指向这条知识要防的那个行为（选最省事的同族复读）。声明为 NP-A「不设期限」与题干自相矛盾。

而母本的 `失效类型` 是「agent 拿到第二视角 verdict 容易**走捷径**」——走捷径本身就是动机措辞。**题干的压力和母本的动机描述是同一件事**，这一条测出来的是压力下做不做，不是无压力下会不会做。

处置：要么把「临界路径」删掉、只保留 correctness-critical（stakes 而非 deadline），要么承认它属护栏档、按 §3.3 移出。**倾向前者**——去掉之后任务仍然承重（设计一件 correctness-critical 产物的验收安排，够不够格用同族复读，这一问依然成立）。

**边界两条（不建议改，但审阅要留痕）**

`pacing.usage-estimate-tension`（「配额侧发出减速信号」）与 `routing.qualification-and-fallback`（「其中候选 A 自身无容量读数」，且母本失效描述明写「容量紧张时」）。两者的资源紧缺都是**判断对象**而非**施加给被测者的压力**，我倾向判它们不违反 §1.2。但 `routing.qualification-and-fallback` 已因另一个理由（Q1-C 档位串档）需要处理，两处一起解决即可。

**已被 §0.5 移出的那批里，压力最重的两条（`capacity.ranking-and-contraction` 的「配额吃紧」、`multilayer.admission-and-escalation`）都已经不在测试范围内**——档位重判顺带清掉了这类，这是个好结果。

## 要改的清单

### 必须改才能跑（5 项）

1. **把提示词写死进预注册，再审一次。** 每条 73 项的**逐字提示词**必须在跑之前落进表里（或落进一份配套 fixture 文件），由**不是提示词作者的人**过一遍。不写死等于没预注册；现场写等于把 §3 的利益冲突从设计挪到执行。

2. **加一道泄题闸，并把结果记进每条记录。** 照试点 §11 的办法：每条提示词单独交给一个未掌握该知识点的第三方，只问「这道题显然期望执行者做什么」。判定分三档并**写进运行记录**：
   - `未泄` → 结果按第 0 层计，可进候选删除批；
   - `半泄` → 结果按第 0 层计但降一级证据等级，需在台账注明；
   - `泄` → **结果按第 1 层计，只能授权「压成线索」，不得进候选删除批**（§5.1 硬约束）。

   优先审 Q2 列出的 19 条「评审 / 判断 / 分类 / 排序」形状条目。**这一步不做，跑出来的数据无法区分第 0 层与第 1 层，整轮结论作废。**

3. **`control.decision-program` 的承重任务重做。** 现在的场景用纯算术就能通过（盲测第三方直接给出了通过答案）。要让线性检查表可证明地漏东西——例如派发会当场解锁新的 ready 节点，或存在需过 fill-work 准入的活。

4. **`slicing.example-contrast` 从 §2 移进 §3.2（类型 B）。** 它与已改档的 `slicing.walking-skeleton` 共享同一失效面，母本自陈不单独定义判断标准，X 的基线发生率过低。它的结构与 §3.2 那三条同型，应走批级消融而非第 0 层。表已标「档位疑议」但处置不够。

5. **`verification.heterogeneous-review` 的题干删掉「临界路径」。** 它与自己声明的 NP-A「不设期限」直接矛盾，且压力方向正对着这条要防的行为。删掉后任务仍承重。

### 可以边跑边改（6 项）

6. **三条档位串档的重判**（`routing.qualification-and-fallback` / `oop.abstraction-cost` / `devloop.ledger-when`）。母本 `失效类型` 正文是纯动机措辞而 tag 写「主体：事实方法」。建议照 §0.5 的流程由第二方重判一次。**在重判出结果之前，这三条的第 0 层通过只授权「压成线索」，不得进候选删除批**——这样跑不必停。（`scheduling.node-contract` 与 `outside.falsification-and-calibration` 母本已自标「双重性质」，不在此列，可照跑。）

7. **`scheduling.dag-and-critical-path` 的 X 重写。** 删掉「也没有写出可复核的逐节点推导」这个逃生舱；并明确跑测环境是否提供图分析工具——两种环境下这条 X 分别恒真与恒假。另需补上母本主张的另一侧（平凡小图上仪式性跑工具）或在台账里显式标注「本条只测了一侧」。

8. **`oop.abstraction-cost` 的 X 删掉第二个合取项**（循环论证判定）。第一项已可判，第二项只会制造双评分歧。

9. **`craft.shared-spine` 降级为参考性证据。** X 依赖被测者自发产出矛盾，k=3 分不开能力与运气。别把它当 k 次全中的存在性证据源。

10. **给 X 的布尔结构补括号 / 改成编号判定步骤。** 至少 `workflow.admission`、`craft.layered-thinking`、`oop.failure-radar` 三条的「A 或 B；且 C」存在两种读法。可在第一批双评出现分歧时集中修。

11. **`distill.routing-tree` 的 X 从判用词改为判路由结果。** 现在它几乎完全落在「有没有说出那三问」上。

### 不用改（点名保留，避免下一位审阅者重开）

## 我拿不准的地方（明说）

1. **泄题的容忍阈值我定不了。** 我给了三档判定，但「半泄」的边界（第三方说对了方向、没说中具体条款，例如 `verification.heterogeneous-review`）该按第 0 层还是第 1 层计，我没有依据可以援引。这需要拍板，而且**应当在跑之前拍**，否则会变成事后按结果挑标准。

2. **我自己的盲测样本只有 6 条，且是我挑的。** 我挑的时候刻意混了「看起来会泄」与「看起来不会泄」两类，但这仍是便利抽样，不是随机抽样。4/6 这个比率不能当成对 73 条的估计。真正的泄题率要靠必改项 2 那道闸跑全量才知道。

3. **「场景事实 vs 施加压力」这条线我划得不硬。** §4.1 自己也提出了这个问题（「同侪在推进」算不算压力）。我判「临界路径」是压力、「配额读数」不是，依据是前者直接陈述延迟代价、后者只是待读的数据。这个区分讲得通，但我不认为它经得起对抗性推敲。若有人给出相反判定，`pacing.usage-estimate-tension` 与 `routing.qualification-and-fallback` 也要跟着移。

4. **我没有验证「73 条各自的母本是否真的支持表里那句『一句话它教什么』」。** 我抽查的 15 条里这个映射都是准的（我逐条读了母本的权威陈述段），但剩下 58 条没查。如果某条的概括偏了，它的承重任务会整条对着错的靶子。这是本次审查**没有覆盖到的一块**。

5. **成本我没算。** 73 × k≈5 ≈ 365 次运行，外加必改项 2 的泄题闸（73 次额外调用）。这个量级值不值，不在我的判断范围里——但试点 §9.6 那条「新增成本可能超过节省」的教训对这里同样适用，跑之前应当算一次。
